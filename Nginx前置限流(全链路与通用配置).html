02 · limit_req_zone：Nginx 自己的共享计数空间

Key：谁的一桶？

$binary_remote_addr 是客户端 IP 的二进制形式。同一 IP 的请求映射到同一桶。

Zone：桶放在哪里？

seckill_gateway_ip:10m 是共享内存区：名称由你命名，10m 是给键与限流状态的内存。

Rate：怎样漏水？

250r/s 表示该 Key 平均每 4ms 漏出一个请求的额度；它不是“每秒整点重置”。

# http 块：声明共享计数空间，所有 worker 可见
limit_req_zone $binary_remote_addr zone=seckill_gateway_ip:10m rate=250r/s;

# location 块：实际使用上面声明的空间
limit_req zone=seckill_gateway_ip burst=200 nodelay;

关键关系：`zone=seckill_gateway_ip` 不是后端服务名，也不是 Redis Key；它只是 Nginx 配置进程内的共享内存区名称。配置加载后，所有 Nginx worker 都根据同一个 IP 去读写这块内存，因此多个 worker 不会各算各的。

03 · 你的秒杀 location：匹配 → 限流 → 转发

Nginx 先选中最长匹配的 location，再执行其中的限流和代理规则。因此 /api/voucher-order/seckill/ 会优先于 /api 命中。

location /api/voucher-order/seckill/ {
    limit_req zone=seckill_gateway_ip burst=200 nodelay;
    limit_req_status 429;
    error_page 429 = @seckill_rate_limited;

    proxy_http_version 1.1;
    rewrite ^/api/(.*)$ /$1 break;
    proxy_set_header Connection "";
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_pass http://hmdp_backend;
}

location @seckill_rate_limited {
    return 429 '{"success":false,"errorMsg":"请求过于频繁，请稍后重试","layer":"nginx"}';
}
匹配路径

请求 /api/voucher-order/seckill/12 命中专用 location，而不是后面的通用 /api。因为它的前缀更长、更具体。

检查 Nginx 共享桶

以 $binary_remote_addr 为 Key 到 seckill_gateway_ip 查状态。超过 rate 但未超过 burst 时，nodelay 让请求立即继续；超过 burst 直接返回 429。

改写后端路径

rewrite 把 /api/voucher-order/seckill/12 变成 /voucher-order/seckill/12，正好匹配 Spring 的 @RequestMapping("/voucher-order")。

携带可信来源信息转发

Nginx 设置 Header，复用与 upstream 的 HTTP/1.1 连接，转给 127.0.0.1:18081。

输入一个路径，再点击“模拟匹配”。

burst 与 nodelay：你的 250r/s + 200 到底意味着什么？

配置瞬时多出的请求用户体验适合场景
无 burst立即拒绝最硬，峰值很容易 429绝不允许突发的内部保护
burst=200排队，按 250r/s 逐步放行延迟可能明显升高允许排队且超时可接受
burst=200 nodelay立即通过最多 200 个突发请求低延迟，但后端要能承受短峰你的秒杀网关粗粒度削峰

准确理解：这不是“每秒允许 250 + 200 = 450 个”。250r/s 是稳定速率；200 是可容忍的超额突发容量。秒杀的最终库存和用户级保护仍由 Redis Lua 与业务限流承担。

04 · IP 与 Header：谁能代表真实客户端？

$remote_addr 是 Nginx 内建变量；X-Real-IP 与 X-Forwarded-For 是 HTTP 头名。你的网关覆写它们的目的，是不信任浏览器自己伪造的 Header。

直连公网：浏览器 → Nginx → Java

使用 $remote_addr 合理；它就是 Nginx TCP 对端的用户 IP。将 X-Real-IP 与 X-Forwarded-For 都覆写为它，后端读取的 IP 可被信任。

有 CDN/SLB：用户 → CDN → Nginx → Java

此时 $remote_addr 是 CDN/SLB IP。要先用 set_real_ip_from 白名单信任上游网段并还原 IP，之后才可将结果交给限流与后端。

两种部署，写法不能混用

部署拓扑Nginx 限流 Key给后端的 Header 写法
用户直接访问 Nginx$binary_remote_addrX-Real-IP $remote_addr；X-Forwarded-For $remote_addr
可信 CDN / SLB 在前还原后的 $binary_remote_addrX-Real-IP $remote_addr；X-Forwarded-For $proxy_add_x_forwarded_for
# 仅在前方 CDN / SLB 的出口网段可信时使用；网段必须替换为实际值
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 192.168.0.0/16;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# 到这里后，$remote_addr 才已还原为可信的客户端 IP
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

安全底线：不能在未设置可信上游白名单时，直接相信客户端传来的 X-Forwarded-For。否则攻击者可以自报任意 IP，绕过按 IP 的限流或伪造审计日志。

05 · 通用扩展：按什么维度限，怎样落配置？

limit_req_zone 里的第一个参数是“限流身份”。Nginx 已有变量和请求头变量可以组合成 Key；zone 名称则完全由你命名。不同接口应分开建 zone，不能一把尺子量所有流量。

公开读接口

按 IP。挡爬虫和突发访问，容忍 NAT 下的少量误伤。

开放平台 API

按 API Key。额度跟调用方绑定，比 IP 更公平。

高价值写接口

网关按 IP 粗保，后端再按用户、资源执行业务限流。

模板 A：公开查询接口，按 IP

# http 块
limit_req_zone $binary_remote_addr zone=public_ip:10m rate=20r/s;

# server 块
location /api/search/ {
    limit_req zone=public_ip burst=40 nodelay;
    limit_req_status 429;
    proxy_pass http://backend;
}

模板 B：开放平台，按 API Key

# X-Api-Key 自动映射为 $http_x_api_key；空 Key 会共用同一个空桶
limit_req_zone $http_x_api_key zone=partner_key:10m rate=100r/m;

location /open-api/ {
    # 生产上应先鉴权并拒绝缺失 Key，再进行该限流
    limit_req zone=partner_key burst=20;
    limit_req_status 429;
    proxy_pass http://backend;
}

模板 C：登录接口，IP 限流 + 并发连接限制

# http 块：请求速率与并发连接是两件事
limit_req_zone  $binary_remote_addr zone=login_ip_rate:10m rate=5r/m;
limit_conn_zone $binary_remote_addr zone=login_ip_conn:10m;

location = /api/user/login {
    limit_req  zone=login_ip_rate burst=3 nodelay;
    limit_conn login_ip_conn 10;
    limit_req_status 429;
    proxy_pass http://backend;
}

模板 D：秒杀 / 抢购，Nginx 与 Redis 各做自己擅长的事

层限流 Key目标是否跨多台网关
NginxIP尽早拦截洪峰，保护 Java 连接、线程与 Redis否。每台 Nginx 各有自己的共享内存
Redis Lua券 + 场景 + IP / 用户全局业务额度、用户公平性、动态降级是。所有业务实例访问同一 Redis 集群
Lua 预扣券 + 用户 + 库存一人一单、不超卖、原子接受请求是
# 你的 Nginx：只做很早、很便宜的第一道防线
limit_req_zone $binary_remote_addr zone=seckill_gateway_ip:10m rate=250r/s;

location /api/voucher-order/seckill/ {
    limit_req zone=seckill_gateway_ip burst=200 nodelay;
    limit_req_status 429;
    error_page 429 = @seckill_rate_limited;
    proxy_pass http://hmdp_backend;
}

location @seckill_rate_limited {
    add_header X-Rate-Limit-Layer nginx always;
    return 429 '{"success":false,"errorMsg":"请求过于频繁，请稍后重试","layer":"nginx"}';
}

06 · 生产避坑与排错顺序

确认限流对象是不是“真实用户”

直连 Nginx 才用 $binary_remote_addr。若有 CDN/SLB，先配置可信网段和 real_ip；否则所有用户可能被识别为一个 SLB IP，或被伪造 Header 绕过。

区分单机 Nginx zone 与全局限流

zone 是单个 Nginx 实例的共享内存，不会同步到另一台网关。两台网关各 250r/s，整体理论入口可能达到 500r/s。需要全局公平配额时交给 Redis、网关集群能力或专用限流服务。

不要让网关替业务做最终正确性判断

Nginx 只能看网络侧 Key，不能安全理解登录用户、券状态、库存或一人一单。因此秒杀仍必须在 Redis Lua 中原子校验和预扣。

谨慎重试代理的 POST

proxy_next_upstream error timeout 在多个 upstream 后端时可能让请求重新投递。下单接口必须带幂等订单号 / Lua 幂等性；否则网络超时不等于后端未处理。

让 429 可观测

保留独立 access_log 或在响应中写入 X-Rate-Limit-Layer。监控 Nginx 429、Java 429、Redis 限流拒绝与 Redis 延迟，才能判断到底在哪层收紧。

排查：为什么“我以为限流了，实际没限”？

现象优先检查结论 / 修复
秒杀请求没有 429实际 URL 是否有结尾斜杠；是否命中专用 location检查 access log 中的请求 URI；用更精确的 location 或统一客户端路径

最后的配置检查清单

位置正确

limit_req_zone 位于 http；limit_req 位于 location 或 server；专用秒杀 location 比通用 /api 更具体。

身份可信

先处理 CDN/SLB 的 real_ip；不盲信浏览器自带的 X-Forwarded-For。

层次分明

Nginx 拦洪峰，Redis 控全局业务频率，Lua 保正确性，数据库做最终持久化约束。
