HM-DIANPING · SECKILL ORDER PIPELINE

秒杀下单链路
从洪峰请求到最终一致

这份文档只讲当前项目真实实现：入口多层限流、Redis Lua 原子受理、Redis Handoff、MySQL Outbox、Kafka 落库、重试、死信与对账补偿。每一层都回答三个问题：为什么要它、代码如何做、它消除了哪个故障窗口。

阅读路径：1. 全景2. 多层限流3. Lua 原子受理4. 为什么有 Handoff5. Outbox/Kafka6. 消费落库7. 状态与失败恢复8. 对账补偿9. 面试复述

1. 先建立全景：这不是“下单接口”，而是一条可靠受理链路

秒杀的第一目标不是立即把订单写进 MySQL，而是以极低延迟、原子地决定“这个用户是否获得购买资格”，随后异步且可恢复地把资格转成数据库订单。

Nginx 粗限流→Redis IP/用户令牌桶→资格令牌→Lua：校验/预扣/去重→Redis Handoff→MySQL Outbox→Kafka→订单落库
层核心职责不是它负责的事
限流提前拒绝无意义/过量流量，保护线程、Redis、下游。不决定库存与订单正确性。
Lua在一个原子边界内预扣库存、保证一人一单。不承担 MySQL 持久化。
Handoff + Outbox跨越 Redis 原子预扣与 MySQL 可持久事件之间的崩溃窗口。不直接创建业务订单。
Kafka 消费者异步批量创建订单、扣数据库库存、完成 Outbox。不依赖“只收到一次消息”。
核心语义：入口成功代表“Redis 已原子接受这次购买资格”，不代表订单已同步落库；因此客户端得到 orderId 后应查询状态，系统允许短暂 PROCESSING。

2. 多层限流：越靠前越便宜，越靠后越精确

2.1 网关层：Nginx 先削掉明显洪峰

# nginx.conf：只针对 /api/voucher-order/seckill/
limit_req_zone $binary_remote_addr zone=seckill_gateway_ip:10m rate=250r/s;

location /api/voucher-order/seckill/ {
    limit_req zone=seckill_gateway_ip burst=200 nodelay;
    limit_req_status 429;
    error_page 429 = @seckill_rate_limited;
    proxy_set_header X-Real-IP $remote_addr; # 覆盖客户端伪造来源 IP
    proxy_pass http://hmdp_backend;
}

它按 Nginx 实际看到的来源 IP 做粗粒度漏桶限流：稳态每秒 250 个请求，额外允许 200 的瞬时突发，超过直接返回 429。结果是异常流量不进入 Java 线程池、更不消耗 Redis 命令。

2.2 应用层：按“券 + 场景 + IP/用户”做分布式令牌桶

// VoucherOrderController：领资格令牌与正式下单各经过一次限流
seckillRateLimitService.check(voucherId, user, clientIp,
        SeckillRateLimitScene.SECKILL_ORDER);
return voucherOrderService.seckillVoucher(voucherId, accessToken);

默认配置是每张券、每种场景下：IP 桶 200 次 / 秒，用户桶 2 次 / 秒。IP 桶处理同网段/脚本洪泛；用户桶处理同一个登录用户快速重放。key 含 {voucherId}，让同一秒杀券的相关 key 在 Redis Cluster 中落入同一槽位，便于 Lua 原子执行。

// SeckillRateLimitServiceImpl：一次 Lua 同时检查两个桶
String ipBucketKey = "seckill:rate:ip:{" + voucherId + "}:order:" + normalizedIp;
String userBucketKey = "seckill:rate:user:{" + voucherId + "}:order:" + userId;
Long result = stringRedisTemplate.execute(TOKEN_BUCKET_SCRIPT,
    Arrays.asList(ipBucketKey, userBucketKey, policyKey),
    ipWindowMillis, ipCapacity, userWindowMillis, userCapacity,
    userCapacityMultiplier, admissionMultiplier);

2.3 Lua 令牌桶为什么不拆成两次 Redis 调用

-- seckill_token_bucket.lua：先预览两个桶，只有都允许才一起消费
local ipTokens, ipAllowed = preview(ipBucketKey, ipWindowMillis, ipCapacity)
local userTokens, userAllowed = preview(userBucketKey, userWindowMillis, userCapacity)
local allowed = ipAllowed and userAllowed
persist(ipBucketKey, ipWindowMillis, ipTokens, allowed)
persist(userBucketKey, userWindowMillis, userTokens, allowed)

若拆成“先扣 IP 令牌、再扣用户令牌”，用户桶失败时可能白白消耗 IP 令牌。Lua 让“两个桶是否都通过”和“是否同时扣令牌”处于一个 Redis 原子边界。

2.4 动态收紧：下游越堵，入口放行越少

// SeckillOrderPressureService：每秒统计可靠受理积压
long current = outboxMapper.countBacklog(); // PENDING + SENT
if (current >= criticalBacklog) update(current, "CRITICAL", 0.1D);
else if (current >= warningBacklog) update(current, "WARNING", 0.5D);
else update(current, "NORMAL", 1.0D);

默认积压超过 1000 时，入口容量乘 0.5；超过 5000 时乘 0.1。它解决“Kafka/数据库已经落后，入口却仍按固定 200r/s 放行”的正反馈雪崩。VIP/高价值用户可有更高个人容量倍率，但自适应压力倍率仍会总体收紧。

限流的边界：限流只是削峰和防刷；它不是库存一致性方案。即使限流完全失效，Lua 仍必须保证不能超卖；反过来，即使 Lua 正确，缺少限流也会让 Redis 成为流量瓶颈。

3. Lua 原子受理：一人一单和不超卖如何同时保证

3.1 资格令牌：把“拿资格”与“真正抢购”拆开

先调用 GET /seckill/token/{voucherId}，服务端对“券 + 用户”生成一个 30 秒令牌。重复领取不会不停生成新令牌，而是返回未过期的旧令牌：

-- seckill_access_token_issue.lua
local existing = redis.call('GET', key)
if existing then return existing end
redis.call('PSETEX', key, ttlMillis, candidate)
return candidate

令牌不是订单正确性的最终依据，它的作用是提前过滤未经过领资格入口的请求、缩短有效攻击面。关键在于：令牌的校验与删除不单独在 Java 里做，而被放进下单 Lua。

3.2 正式下单时，Java 只发起一次 Lua

// VoucherOrderServiceImpl.seckillVoucher()
Long code = stringRedisTemplate.execute(SECKILL_SCRIPT, Collections.emptyList(),
    voucherId.toString(), userId.toString(), String.valueOf(orderId),
    String.valueOf(System.currentTimeMillis()), accessToken == null ? "" : accessToken,
    tokenEnabled ? "1" : "0");

3.3 一次脚本内的操作顺序

-- seckill.lua：省略活动时间/状态判断后的关键部分
if tonumber(redis.call('get', stockKey)) <= 0 then return 1 end        -- 无库存
if redis.call('sismember', orderKey, userId) == 1 then return 2 end -- 已购
if accessTokenEnabled and redis.call('get', accessTokenKey) ~= accessToken then return 7 end
if accessTokenEnabled then redis.call('del', accessTokenKey) end
redis.call('incrby', stockKey, -1)          -- 预扣库存
redis.call('sadd', orderKey, userId)             -- 记录“该用户已购”
redis.call('zadd', handoffKey, currentTime, handoffMember)
redis.call('hset', acceptedKey, orderId, userId .. '|' .. voucherId)
return 0

为什么一人一单成立

orderKey 是按券划分的 Redis Set；同一用户第二次请求看到 SISMEMBER=1 直接返回。检查与 SADD 同在 Lua，因此不存在并发窗口。

为什么不超卖成立

库存检查与 INCRBY -1 同在 Lua 原子执行。两个并发请求不可能都在同一份库存上各自看到“还有最后 1 件”。

为什么不能写成 Java 的 if + decrement：两个请求可能都读到库存为 1，再分别扣减，造成超卖。分布式锁可以缓解但增加往返和锁竞争；对 Redis 内部多 key 状态变更，Lua 提供了更小、更清晰的原子边界。

Lua 成功后接口会立即返回 orderId + SUCCESS；若 Redis 执行异常，系统返回“结果未确认”，而不是武断认定失败，因为客户端可能在 Redis 已执行成功、但响应丢失后重试。

4. 为什么 Outbox 前还需要 Redis Handoff？

因为 Lua 中的 Redis 原子提交和 MySQL Outbox 插入不在同一个事务里。Handoff 是专门保护两者之间崩溃窗口的临时交接队列。

没有 Handoff
Lua 预扣成功 → 应用准备写 MySQL Outbox → 进程宕机。此时 Redis 库存已减、用户已标记购买，但 MySQL 没有事件；Kafka 不会有消息，订单可能永远不落库。
有 Handoff
Lua 预扣成功 时，同步 ZADD seckill:order:handoff:{voucherId}；即便 Java 随后宕机，后台 Handoff Relay 仍能从 Redis 读出该订单并转成持久化 Outbox。
-- Lua 内交接记录：ZSet score 是受理时间，member = orderId|userId|autoIssued
local handoffMember = orderId .. '|' .. userId .. '|0'
redis.call('zadd', handoffKey, currentTime, handoffMember)

// Handoff Relay：常驻线程，每轮按券取最早的一批
Set<String> members = handoffService.findFirst(voucherId, batchSize);
SeckillOrderOutboxEvent event = handoffService.parse(voucherId, member);
batchWriter.insertCommitted(events);       // MySQL 事务插入 Outbox
handoffService.completeBatch(voucherId, events, members); // 成功后才从 Redis 删除

Handoff Relay 使用 Redis 租约保证多实例中一个活跃工作者处理；MySQL 插入失败时成员保留在 ZSet 中，按 100ms 到 5s 指数退避重试。遇到格式错误或数据完整性冲突，单条隔离到 quarantine，避免一条坏记录堵住整批。

4.1 “先删 Handoff 再写 Outbox”为什么绝对不行

顺序崩溃后果项目选择
先删 Handoff，后写 Outbox删成功后崩溃，订单永久消失。不采用。
先写 Outbox，后删 Handoff写成功后崩溃，可能重复转存。采用；Outbox 的 eventId=orderId 作为幂等键。
-- seckill_handoff_complete.lua：只在 MySQL 写成功之后执行；一次原子清理
redis.call('ZREM', handoffKey, unpack(members))
redis.call('HDEL', acceptedKey, unpack(orderIds))

acceptedKey 是短暂的“已接受订单归属凭证”：Outbox 尚未生成时，状态查询还能确认该 orderId 属于当前用户，并返回 PROCESSING。

5. MySQL Outbox 到 Kafka：可靠投递，而非幻想中的跨库事务

5.1 Outbox 是什么

Outbox 表把“已接受的订单事件”持久化到 MySQL。状态机为 PENDING → SENT → COMPLETED；异常可进入 MANUAL_REVIEW。它是 Kafka 投递的可靠来源，也是状态查询与对账的依据。

// SeckillOrderOutboxEvent.pending()
return new SeckillOrderOutboxEvent()
  .setEventId(String.valueOf(orderId)) // 订单 ID 即幂等事件 ID
  .setOrderId(orderId).setVoucherId(voucherId).setUserId(userId)
  .setStatus(STATUS_PENDING).setRetryCount(0).setNextRetryTime(now);

5.2 Outbox Relay 如何并发安全地发送

// SeckillOrderOutboxRelay：默认每 100ms 扫描
List<Event> events = outboxMapper.findDispatchable(batchSize);
LocalDateTime leaseUntil = LocalDateTime.now().plusSeconds(relayLeaseSeconds);
if (outboxMapper.claimRelayBatch(candidateIds, relayOwner, leaseUntil) == 0) return;
List<Event> claimed = outboxMapper.findClaimedBatch(candidateIds, relayOwner);
dispatchBatch(claimed);

订单 Relay 不依赖 Redis 锁，而是使用 MySQL 行级租约抢占事件。原因是：当 Redis Sentinel 故障转移或 Redis 不可用时，已持久化的订单仍应可继续投递；MySQL 是 Outbox 的权威存储。

// 生产者：按 voucherId 作为 Kafka key，同一张券保持分区内顺序
return kafkaTemplate.send(topic, String.valueOf(message.getVoucherId()), message);

// 真实 Kafka 消息 JSON
{
  "eventId": "123456789", "outboxId": 88, "orderId": 123456789,
  "voucherId": 12, "userId": 1001, "autoIssued": false,
  "occurredAtEpochMillis": 1761019200000
}

生产者配置了 acks=all、enable.idempotence=true：只有 ISR 副本确认后才算发送成功，网络重试也不会让同一次 producer send 重复追加。

仍然是至少一次：Kafka 确认成功后、Relay 把 Outbox 标为 SENT 前若宕机，事件会再次发送。系统刻意接受重复，并在消费者用幂等落库处理；这比“为了避免重复而可能丢订单”安全得多。

6. Kafka 消费：手动 ACK 只发生在数据库事务成功之后

// SeckillOrderKafkaConsumer：批量消费
@KafkaListener(topics = "${hmdp.kafka.seckill-order.topic}",
  groupId = "${hmdp.kafka.seckill-order.consumer-group}",
  containerFactory = "seckillOrderKafkaListenerContainerFactory")
public void onMessage(List<SeckillOrderMessage> messages, Acknowledgment acknowledgment) {
    List<VoucherOrder> orders = consumerService.createOrders(messages);
    acknowledgment.acknowledge(); // 创建订单事务成功后才提交 offset
    for (VoucherOrder order : orders) afterOrderCreated(order);
}

消费者配置为 enable-auto-commit=false、批量监听、AckMode.MANUAL。业务异常时不 ACK，框架按固定退避重试 3 次；仍失败会同步写入 DLT。DLT 消费者尝试将 Outbox 事件重新入队，彻底失败则标记人工核对。

6.1 消费端幂等：重复消息不会重复建单或重复扣 DB 库存

// VoucherOrderPersistenceServiceImpl：按券分组，批量 INSERT IGNORE
int inserted = voucherOrderMapper.batchInsertIgnore(orders);
if (inserted < orders.size()) verifyIgnoredOrdersExist(orders);
if (inserted == 0) continue; // 本批全是重复投递，不再扣库存

int updated = voucherOrderMapper.decrementStock(voucherId, inserted);
if (updated != 1) throw new DatabaseStockMismatchException(voucherId, inserted);

数据库用订单唯一约束（用户 + 券）和订单 ID 约束兜底。第一次消息创建订单后，即使 Kafka 因 ACK 前宕机而重投，INSERT IGNORE 会忽略已存在订单；只有真正插入的数量才参与数据库库存扣减。

两层一人一单：Redis Set 负责高并发入口的快速拒绝；MySQL 唯一约束负责异步、重试、灾难恢复场景的最终兜底。不能只依赖 Redis，也不能只依赖 MySQL。

7. 状态查询、失败重试与人工核对

// VoucherOrderServiceImpl.querySeckillOrderStatus() 的查找优先级
1. tb_voucher_order 有订单 → SUCCESS / CANCELLED
2. tb_seckill_order_outbox 有事件 → PROCESSING / MANUAL_REVIEW
3. Redis acceptedKey 有归属凭证 → PROCESSING
4. 都没有 → 未受理或不存在

这解释了为什么接口返回订单 ID：客户端不必盲目重复抢购，而是轮询状态。Handoff/Outbox 的存在让“已经接受、但尚未持久化”的订单有可解释状态。

Kafka 消费多次失败时发生什么？

订单消息进入 DLT 后，SeckillAcceptedOrderRecoveryService 先查询订单是否其实已落库：若已存在，直接将 Outbox 标记完成；若未存在，则按指数退避把该事件重新设为可投递。重入队也失败时标为 MANUAL_REVIEW，定时任务每 5 秒尝试恢复人工核对项。因为用户资格已经在 Lua 中被接受，不能简单回滚资格并告诉用户失败。

8. 为什么仍需对账补偿：重试解决单点失败，对账修复状态漂移

重试只知道“某一步报错了”。现实中还会出现进程崩溃、Redis 数据丢失/重启、Handoff 与 Outbox 删除时序、人工处理等无法由单次重试覆盖的状态漂移。因此项目定时以 MySQL 的订单与 Outbox 为权威，重建 Redis 秒杀投影。

8.1 对账时如何计算正确库存

// SeckillOrderReconciliationService.reconcileVoucher()
List<Event> unpersisted = outboxMapper.findUnpersistedEvents(voucherId);
reservedOrderIds.addAll(unpersisted.orderId);       // 已受理但还没订单的预留
purchasedUserIds.addAll(voucherOrderMapper.findActiveUserIds(voucherId)); // 已落库用户
int handoffOnly = mergeHandoffReservations(...);    // Lua 成功、Outbox 尚未存在的窗口
int expectedStock = max(0, mysqlVoucherStock - reservedOrderIds.size() - handoffOnly);

它不能只用“已落库订单数”计算库存，否则已经 Lua 预扣、正在 Handoff/Outbox 排队的资格会被重新放回库存，导致超卖。对账把三类占用都纳入：

来源表示什么是否扣除 Redis 可售库存
MySQL 已创建订单最终持久化购买者是，并重建到已购 Set。
Outbox PENDING/SENT/MANUAL_REVIEW 且未落库已接受、等待持久化的预留是。
仅在 Handoff 的记录Lua 成功、尚未写入 Outbox 的临时预留是。

8.2 重建时为什么要暂停新预扣

-- seckill.lua 开头：对账锁存在即拒绝新请求
if redis.call('exists', recoveryKey) == 1 then return 8 end

-- seckill_rebuild.lua：确认恢复 token 后，原子替换库存和已购用户集合
redis.call('SET', stockKey, expectedStock)
redis.call('DEL', orderKey)
redis.call('RENAME', stagingOrderKey, orderKey)
redis.call('DEL', recoveryKey)

若对账时仍允许新的 Lua 预扣，快照计算与新请求会交叉，重建可能覆盖刚刚发生的扣减。因此每张券有独立 recoveryKey 租约；重建期间请求得到“秒杀数据正在恢复，请稍后重试”。先把用户集合写入 staging key，再通过 Lua 原子替换，避免消费者看到半成品集合。

权威边界：Redis 是高并发准入投影，MySQL 的订单和 Outbox 是最终可恢复事实。对账不是常规成功路径，而是处理 Redis 重启、部分失败和长尾事件后的最终收敛机制。

9. 面试复述与高频追问

90 秒版本：秒杀入口先通过 Nginx 对 IP 粗限流，保护 Java 和 Redis；进入应用后，使用 Redis Lua 同时执行“券维度的 IP 桶、用户桶”，并结合 Outbox 积压动态收紧容量。用户先获取短期资格令牌，正式下单时 Lua 在同一原子边界内校验活动、库存、重复购买和令牌，再完成库存预扣、用户已购标记，并写入 Redis Handoff。Handoff 用于保护 Redis 预扣成功到 MySQL Outbox 落库之间的崩溃窗口；后台 Relay 将它可靠转存为 Outbox。Outbox Relay 使用 MySQL 租约抢占事件，Kafka 以 voucherId 分区发送，消费者在本地事务中批量 INSERT IGNORE 订单、按真实插入量扣数据库库存，并在成功后手动 ACK。整条链路按至少一次设计，重复投递通过 Redis Set、MySQL 唯一约束和幂等落库处理；DLT、恢复任务与定时对账负责处理长尾失败和 Redis 投影漂移。

Q：既然有 Outbox，为什么还需要 Handoff？

Outbox 必须先写入 MySQL，但 Lua 的 Redis 预扣已成功时，应用可能在写 Outbox 前宕机。Handoff 是这段跨存储事务间隙的临时、可恢复记录；没有它，资格已占用却没有可投递事件。

Q：为什么不能承诺“消息一定成功、一定只消费一次”？

Kafka 确认后、更新 Outbox 状态前宕机必然可能造成重发。项目选择至少一次投递，把正确性建立在幂等消费之上；这是更可靠的工程取舍。

Q：数据库库存和 Redis 库存为什么都要扣？

Redis 库存是高并发实时准入的投影，确保不超卖；MySQL 库存与订单是最终持久化事实。异步阶段有短暂差异是正常的；靠 Outbox、重试与对账最终一致，而不是假装两者能原子同时更新。
