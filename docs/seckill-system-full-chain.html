01 / CONTRACT

先定义“成功”到底是什么

用户的点击先在 Redis 锁定资格，订单在异步事务提交后才真正创建。两个事实由不同状态表达，不能因为 HTTP 请求成功就展示“订单已创建”。

Redis acceptance

资格已锁定

Lua 原子预扣、已购集合写入和 Handoff 留痕成功。接口返回 orderId + PROCESSING。

MySQL commit

订单创建成功

订单插入、MySQL 库存扣减、Outbox 完成处于事务边界；事务提交后才展示 SUCCESS。

Uncertain result

结果未确认

Lua 结果不确定或两侧都不可判定时返回 UNKNOWN；不能凭超时推断用户未抢到。

本链路的恢复方向：优先向前补单

已告知用户“资格已锁定”的请求，不会因为 Kafka 死信、MySQL 暂时故障或库存差额而自动变成 FAILED。最终失败与释放资格仍是未启用的受控业务决策。

03 / DATA · REDIS

Redis 结构：受理事实与恢复线索

以下是默认用户秒杀路径的关键 Key。Lua 一次执行完成检查、预扣、占位和留痕；后续服务不靠“猜”一笔扣减属于谁。

Key / 类型内容作用与清理时机
seckill:meta:{voucherId}
Hash		beginTime / endTime / statusLua 在预扣前检查活动窗口和上架状态。
seckill:stock:{voucherId}
String		Redis 剩余可预留库存Lua 成功时减 1；已受理任务异常时不自动加回。
seckill:order:{voucherId}
Set		已占资格的 userIdSISMEMBER 实现一人一单；用户主动取消才按既有流程移除。
seckill:access:token:{voucherId}:{userId}
String		可选的前置资格令牌启用时由同一 Lua 校验并消费；失败请求不预扣。
seckill:order:handoff:{voucherId}
ZSet		score=受理毫秒；member=orderId|userId|0Redis→MySQL 的待交接任务。确认 Outbox 已提交后删除，崩溃前仍可重试。
seckill:order:accepted
Hash		field=orderId；value=userId|voucherId|acceptedAt|PROCESSING归属校验、MySQL 故障时状态查询、丢失 Outbox 时的恢复凭证；终态后默认保留 7 天。
seckill:order:accepted:user:{voucherId}
Hash		userId → 当前 orderId响应丢失或页面刷新后，按用户和券找回在途订单号。
seckill:order:accepted:audit
ZSet		orderId → 下次巡检毫秒首次 score=受理时间+60 秒；领任务时改为当前时间+5 分钟；终态移除。
seckill:order:accepted:expire
ZSet		终态 orderId → 清理时间终态凭证保留期到期时批量清理 Hash 字段。
原子性边界

库存检查、一人一单、令牌消费、DECR、SADD、Handoff、受理凭证与巡检标记同处一个 Lua 脚本；正常返回码 0 才表示资格受理成功。脚本结果不确定时 API 返回 UNKNOWN。

04 / DATA · MYSQL

MySQL 结构：交接记录、订单与人工轨迹

tb_seckill_voucher

最终交易库存

voucher_id 主键；stock 是 MySQL 端剩余库存。Consumer 只按本次实际新插入订单数扣减：stock = stock - inserted，并检查库存足够。

tb_voucher_order

订单事实

id = orderId 主键。生成列 active_order_marker 对非取消订单取 1、取消订单取 NULL；唯一键 (user_id, voucher_id, active_order_marker) 限制同用户同券至多一笔有效订单，同时允许取消后再买。

tb_seckill_order_outbox

可靠投递记录

event_id 与 order_id 分别唯一。保存 status、retry_count、next_retry_time、last_error、Relay 租约，以及人工核查责任队列和截止时间。

tb_seckill_manual_review_action

人工操作审计

记录 order_id、操作人、动作、原因、时间。动作包含原单号重试、确认完成、申请失败审核；申请审核本身不会产生 FAILED。

-- 消费者同一事务里的核心约束，示意
INSERT IGNORE INTO tb_voucher_order(id, user_id, voucher_id) VALUES (...);
-- 被忽略时必须按 orderId 查历史订单并核对归属，包括已取消订单
UPDATE tb_seckill_voucher
   SET stock = stock - :inserted
 WHERE voucher_id = :voucherId AND stock >= :inserted;
-- 只扣实际新插入数；失败就抛出并回滚整笔事务

迁移来源：V5/V6 建 Outbox 与 Relay 租约，V10 建人工动作表，V11 建有效订单唯一约束，V12 建人工责任与时限字段。

05 / STATES

两套状态机，不互相冒充

用户状态回答“向用户承诺了什么”，Outbox 状态回答“事件处理到哪一步”。Result.ok 只是接口受理成功，不能替代订单状态。

用户可见状态
PROCESSING

Redis 预扣成功，资格已锁定；MySQL 订单未确认提交。

MANUAL_REVIEW

自动消费受阻且任务停车；资格仍保留，等待人工核查。

SUCCESS

同一 orderId 的 MySQL 订单事务已提交。

CANCELLED

用户主动取消已创建订单；属于独立的取消流程。

UNKNOWN

Redis 执行结果或状态数据暂不可判定；不能断言失败。

FAILED · 未启用

需要终态规则、落单栅栏和幂等释放；当前代码没有自动进入该状态。

PROCESSING → SUCCESS / MANUAL_REVIEW → SUCCESS →（用户取消）CANCELLED
Outbox 内部状态
PENDING

事件已持久化，等待 Publisher 按租约领取。

SENT

Kafka 已收到投递；尚需确认消费者已落单，允许重查和重投。

COMPLETED

消费者事务确认订单已处理。重复投递仍可 ACK，不再扣库。

MANUAL_REVIEW

死信处理后停车；不会被自动待投递查询再次领取。

PENDING ⇄ SENT → COMPLETED；消费重试耗尽 → MANUAL_REVIEW → 人工重试 / 确认完成
06 / EXECUTION

正常链路，逐步看提交边界

生成 orderId，检查活动与访问资格

默认订单号由数据库号段服务产生，不是 UUID；请求线程先拿 ID，便于后续查询和全链路幂等。

Redis Lua 原子预扣并留痕 FIRST COMMIT POINT

库存 −1、已购集合加入用户，同时写 Handoff、受理凭证与巡检 ZSet。API 此时返回 PROCESSING 和 orderId。

Handoff Relay 转存 Outbox

后台线程按 Redis 租约工作，空闲默认 20ms 轮询。批量幂等写 MySQL Outbox；确认写入提交后删除 Handoff。崩溃在删除前会再次转存同一事件。

Outbox Relay 投递 Kafka

默认 100ms 调度，按到期时间和租约领取 PENDING/SENT。Publisher 发送成功但未标记 SENT 时允许重发；SENT 默认 60 秒重查。

Consumer 在数据库事务里落单

批次按 orderId 去重，INSERT IGNORE 后核对被忽略订单，按实际新增数扣 MySQL 库存，Outbox 标记 COMPLETED。

事务返回后手动 Kafka ACK SECOND COMMIT POINT

事务失败就抛异常、不 ACK；事务提交后即使 ACK 前崩溃，重放也会按 orderId 幂等跳过。

刷新终态，用户查询 SUCCESS

Redis 受理凭证更新为 SUCCESS 并保留默认 7 天；用户状态查询优先看 MySQL 订单，MySQL 不可用时再看凭证。

07 / WHY AUDIT

有 Kafka 重试，为什么还需要定时对账？

重试只能覆盖“仍在队列里的任务”；对账负责发现“责任链断开的任务”

  1. Redis Lua 已成功，但 MySQL 故障，Handoff 一直没转存；用户已拿到 PROCESSING。
  2. Outbox 已提交，但 Publisher 崩溃、SENT 状态迟迟没有订单；需要按原 ID 重查。
  3. 订单事务已提交、Kafka ACK 前崩溃；再次消费要确认没有重复扣库。
  4. 更严重的是 Handoff、Outbox 或订单某段缺失，仍有受理凭证；单靠 Kafka 消费者看不到这笔任务。
  5. Redis 与 MySQL 库存出现差值，需区分在途预留与无法解释的漂移，保留证据给人工处理。
输送机制

Relay / Kafka 重试

任务已知且仍在可领取队列里，按租约和退避反复推进。它解决暂时性传输或处理失败。

核查机制

定时逐单巡检

从独立受理凭证反查订单与 Outbox，发现链路断点并按原 ID 修复或报警。它不靠总库存差额猜测单笔订单。

时间阈值不是失败判定

没有逐单 Consumer 心跳或栅栏，仅凭“过了 60 秒”“Kafka lag 高”“已进 DLT”无法证明消费者永久失败。定时任务只触发重查、可逆重投、补写 Outbox 和人工升级。

08 / PER-ORDER AUDIT

逐单巡检：凭什么查，按什么顺序补？

受理 Lua 把 orderId 放入巡检 ZSet，score 为受理时间 + 60 秒。默认每 60 秒扫描最多 200 笔；Lua 原子领取一笔，并把 score 推后默认 5 分钟，作为崩溃后可再次领取的租约。

01 / ORDER EXISTS

MySQL 订单已存在

核对 userId、voucherId；Outbox 未完成则补为 COMPLETED；凭证同步 SUCCESS 或 CANCELLED。不再扣库存。

02 / NO ORDER · NO OUTBOX

受理凭证仍可信

用同一 orderId、userId、voucherId 幂等补写 MySQL Outbox。后续 Relay 与 Consumer 继续完成订单；不重新预扣 Redis。

03 / NO ORDER · PENDING OR SENT

已有在途 Outbox

记录等待中的状态，交给 Outbox 租约和退避机制继续投递或重查。下一个巡检租约到期再核实；不立即认定失败。

04 / CONTRADICTION OR PARKED

进入人工关注

MANUAL_REVIEW、COMPLETED 却无订单、凭证缺失或归属冲突：记录错误并核查；绝不凭猜测释放资格。

人工停车的动作边界

默认 Kafka 消费重试 3 次（间隔 1 秒）后发送 DLT；DLT 消费者把 Outbox 置为 MANUAL_REVIEW，默认责任队列 seckill-ops、1 小时截止，每 5 分钟检查超时。操作员可按原 ID 重试、确认已完成、申请终态失败审核。申请只留痕，不执行 FAILED / Redis 库存释放。

09 / AGGREGATE AUDIT

库存对账：先判在途，再看差额

库存汇总任务默认每天 02:00、08:00、14:00、20:00 运行。它用于发现无法由在途任务解释的漂移；当前实现只有读和日志，没有重写 Redis 的定时动作。

Gate / 先暂缓

任何仍在途的证据

先查该券未落单 Outbox、Redis Handoff，以及全局未解决受理凭证 ZSet 的数量。任一非零，就不做库存数值比较，避免把异步滞后误报为库存错误。

Compare / 稳定后核对

库存和已购集合

没有在途证据时，读 MySQL 剩余库存与 Redis 剩余库存；再比较 MySQL 有效订单 userId 集合与 Redis 已购 Set。差异仅写错误日志，交人工调查。

Redis 剩余20↔MySQL 剩余25＋待落单预留5
示例判读

若 5 笔预扣仍在 Handoff / 未落单 Outbox 中，Redis 20、MySQL 25 是异步处理窗口，不触发回补。若没有任何在途证据，差 5 才报警并保留现场；依旧不会自动把 Redis 改成 25。

当前实现的精度限制

未解决受理凭证 ZSet 是全局 Key：一个活动还有待处理任务，其他活动的汇总比较也会暂缓。MANUAL_REVIEW 长期未处理也会使该券持续暂缓；逐单巡检及人工超时日志仍运行。这里的“没有在途”是代码可见证据，不等于数学上证明不存在消费者正在执行。

11 / CONSISTENCY

最终一致性靠哪些可验证的不变量？

Invariant 01

同一资格只受理一次

Redis Lua 的库存检查与 SISMEMBER / SADD 同处原子边界；重复点击不会创建第二笔成功预留。

Invariant 02

同一订单只落库一次

orderId 贯穿 Handoff、Outbox、Kafka 和订单主键。重复 Outbox 有唯一键，重复 Kafka 消息按订单主键核对历史记录。

Invariant 03

MySQL 只扣新订单数

订单插入与 MySQL 扣库在事务内；库存扣减量是实际新插入数。失败抛出回滚，消费者不 ACK。

Invariant 04

任何断点可重新推进

Handoff 待交接、Outbox 租约、Kafka 重投、受理凭证逐单巡检形成多层恢复线索。ACK 发生在事务提交之后。

一致性的含义

在受理凭证和交接记录可用、依赖服务恢复、异常任务得到人工处理的前提下，PROCESSING 任务持续被推进到订单 SUCCESS。Redis 与 MySQL 库存在处理期间允许不同；最终稳定后才适合做汇总核对。这里是“至少一次输送 + 幂等落库 + 补漏巡检”，不是跨 Redis、Kafka、MySQL 的端到端恰好一次事务。

12 / BOUNDARIES

哪些事当前没有自动化？

边界当前行为为什么重要
终态失败与库存释放未启用 只有人工“失败审核申请”留痕。必须先明确不可履约规则、拦住迟到消费者的数据库栅栏、按 orderId 幂等释放及通知规则；死信或超时本身不够。
Redis-only 受理耐久性待决策 D1 默认在 MySQL Outbox 提交前就返回 PROCESSING。若 Redis 中受理凭证和 Handoff 同时丢失，仅凭 MySQL 无法还原已答复用户的资格；定时对账也无法凭空找回。
消费者正在执行的证明当前无逐单消费心跳或栅栏。不能凭 SENT 未落单和时间超限断言消费者已经永久失败，因此只重查、重投或交人工。
自动发券旁支自动发券 Lua 写入 Handoff，但未写用户秒杀路径的 accepted Hash / audit ZSet。Handoff Relay 仍能交接；本文逐单受理凭证巡检专指普通用户秒杀路径，不能声称覆盖自动发券的每一笔。
灾难重建 Redis旧重建服务仅保留人工调用，没有定时自动运行。必须先人工核实受理流水完整，否则从 MySQL 反推 Redis 会覆盖已告知用户的预留。
上线前必须验证

已有有效订单重复数据会阻止 V11 唯一索引迁移；需先清理。完整集成与故障注入还需 Redis、MySQL、Kafka 环境。本文描述的是仓库当前逻辑，不代表这些外部依赖在此桌面文件中运行过。
