# 秒杀链路并发优化复盘

本文记录本项目秒杀链路在并发测试中发现的问题、定位过程、已经实施的优化以及优化前后的测试结果。

## 一、测试环境与统计口径

- 应用：本机单个 Spring Boot 实例，端口 `18081`。
- Redis：Docker 单节点，宿主机端口 `6380`。
- MySQL：Docker 单节点，宿主机端口 `3308`。
- 压测工具：前期使用 Apifox 验证功能，正式性能测试改用 JMeter 5.6.3 非 GUI 模式。
- 用户数据：CSV 中每行一个独立用户 Token，避免把“同一用户重复购买”误算成并发失败。
- 业务成功：不能只看 HTTP 200，还必须检查响应中的 `success`、订单状态以及最终 MySQL 数据。
- QPS 口径：业务压测优先采用 `*-result.json` 中按有效请求窗口计算的 QPS；诊断接口采用 JMeter 日志中的吞吐量。两种口径存在少量启停开销差异。
- 一致性校验：压测结束后同时核对 MySQL 订单数、MySQL 去重用户数、MySQL 库存、Redis 库存、Redis 已购用户数和 Stream Pending 数量。

不同阶段的并发数、持续时间和业务逻辑不完全相同，因此数据用于定位瓶颈和观察趋势，不应把所有阶段简单视为严格的 A/B 实验。

## 二、压测方式不正确导致结果失真

### 问题与测试现象

最初使用 Apifox 的“功能测试”场景进行压测时，把线程数设置为 100，但循环次数由测试数据自动计算。线程会持续循环取数据，并不是“100 个用户各请求一次”。因此出现了以下现象：

- 100 张券却执行了 2,000 多次请求，库存为 0 后仍继续运行。
- “一人一单”测试中大量响应为 `success=false`，但这是重复购买被正常拦截，不等于服务异常。
- 断言只检查 HTTP 200 时，`{"success":false,"errorMsg":"不能重复下单"}` 也会显示测试通过。
- 请求曾发送到 `127.0.0.1:80`，而应用实际监听 `18081`，产生 `ECONNREFUSED`。
- Apifox 展示的“接口请求耗时”可能是所有并发请求耗时之和，不能直接当作整场测试持续时间。

### 优化

1. 功能验证与性能测试拆开：
   - 一人一单验证：同一 Token 请求两次，第一次成功、第二次返回不能重复下单。
   - 多用户秒杀验证：每个线程从 CSV 读取不同 Token，每个用户只请求一次。
2. 正式性能测试改用 JMeter：
   - 使用 `CSV Data Set Config` 提供独立 Token。
   - 使用固定线程数、固定 Ramp-up 和固定持续时间。
   - URL 明确配置为 `127.0.0.1:18081`。
   - 同时校验 HTTP 状态、业务响应和最终数据库结果。
3. 每轮使用新的测试券，或者完整重置该测试券的 MySQL 订单、MySQL 库存、Redis 库存、活动时间和已购用户集合，避免旧数据污染结果。

### 优化后的测试结果

JMeter 首轮可复现测试使用 100 线程、每线程 10 次，共 1,000 次请求：

- 吞吐量：`900.1 req/s`
- 平均响应时间：`5 ms`
- 错误率：`0%`

这个测试持续时间较短，主要作为初始基线；后续峰值测试统一采用固定时长模型。

## 三、Lua 防重不能代替数据库唯一约束

### 问题

Lua 中的 `SISMEMBER seckill:order:{voucherId}` 可以在正常情况下拦截重复请求，但它不是最终一致性约束：

- Redis 数据可能因为重启、过期、人工误删或主从切换而丢失。
- 消息可能重复投递或重复消费。
- Redis 与 MySQL 之间不存在跨系统事务。
- 两条不同订单 ID 的消息可能对应同一个用户和同一张券。

如果数据库没有唯一约束，Redis 防重状态一旦失效，就可能真实插入重复订单。

### 优化

在 `tb_voucher_order` 增加联合唯一索引：

```sql
UNIQUE INDEX uk_user_voucher(user_id, voucher_id)
```

现在形成三层防护：

1. Lua 在入口快速拦截绝大多数重复请求。
2. 消费端按幂等逻辑处理重复消息。
3. MySQL 唯一索引作为最终兜底，保证数据库中一人一单。

同时，消费端不再在正常路径执行 `SELECT COUNT`。批量 `INSERT IGNORE` 直接依靠唯一索引判断是否已经存在，只有发生忽略或冲突时才查询已有订单 ID。

### 优化后的结果

后续所有正式压测中均满足：

- `mysqlOrdersFinal = mysqlDistinctUsers`
- 没有出现同一用户同一券的重复数据库订单
- Redis 库存与 MySQL 库存最终一致

## 四、Lua 缺少活动边界和库存 Key 异常处理

### 问题

仅传入 `voucherId` 并读取库存，无法在 Redis 内原子判断活动是否开始、是否结束。如果先在 Java 查询时间，再执行 Lua，时间校验与扣库存之间会出现竞态窗口。

旧写法直接执行：

```lua
if tonumber(redis.call('get', stockKey)) <= 0 then
    return 1
end
```

库存 Key 不存在时，`GET` 返回 false，`tonumber(false)` 得到 nil，Lua 会运行报错，而不是返回可识别的业务结果。

### 优化

- 使用独立 Key 保存不同数据结构：
  - `seckill:stock:{voucherId}`：String 库存。
  - `seckill:order:{voucherId}`：Set 已购用户。
  - `seckill:meta:{voucherId}`：Hash 活动开始时间、结束时间和可读时间。
  - `seckill:order:result:{orderId}`：Hash 异步订单状态。
- Java 只向 Lua 传入业务参数和当前时间，Lua 从 Redis 读取库存和活动元数据。
- 在一个 Lua 脚本中原子完成时间判断、库存判断、一人一单判断、扣减库存、记录已购用户、写入 Stream 和记录初始订单状态。
- 库存或活动元数据不存在时返回明确错误码，不再抛 Lua 运行异常。
- 应用启动时从 MySQL 检查并恢复缺失的库存 Key，同时刷新活动时间元数据；已有 Redis 库存使用 `SETNX`，避免重启时覆盖正在变化的库存。

### 优化后的结果

接口可以明确区分：

- 库存不足
- 不能重复下单
- 活动配置不存在
- 秒杀尚未开始
- 秒杀已经结束

压测期间没有再因为库存 Key 缺失出现 Lua 的 `nil <= 0` 运行错误。

## 五、落库事务与 ACK 顺序可能造成订单丢失

### 问题

Redis Lua 成功只代表库存已预扣、消息已进入 Stream，不代表 MySQL 订单已经创建。若消费端在事务提交前 ACK，或者业务失败后仍 ACK，可能出现：

```text
Redis 库存已经扣减
前端已经拿到受理结果
Stream 消息已经 ACK
MySQL 订单不存在
```

此外，在同一个类中通过普通方法调用带 `@Transactional` 的方法，会绕过 Spring 代理，事务可能不生效。

### 优化

- 把落库逻辑拆到独立的 `VoucherOrderPersistenceServiceImpl` Spring Bean。
- 在公开落库方法上使用 `@Transactional(rollbackFor = Exception.class)`。
- 订单插入和 MySQL 库存扣减放在同一事务内。
- 顺序调整为：

```text
MySQL 事务提交
    -> 写入 Redis 最终订单状态
    -> ACK Stream 消息
```

- MySQL 已提交但状态写入或 ACK 失败时，不把它当成业务失败，也不再次扣减数据库库存；消息保留在 Pending 中，后续按幂等逻辑恢复。

### 优化后的结果

后续压测结束后均能观察到：

- MySQL 最终订单数等于成功受理且应落库的订单数。
- Stream Pending 最终为 0。
- MySQL 库存与 Redis 库存一致。

## 六、Pending 无限重试会空转并持续刷日志

### 问题

原 Pending 处理逻辑使用无限 `while (true)`。同一条异常消息处理失败后，会立即再次读取并处理，导致：

- CPU 空转。
- Redis 和 MySQL 被无意义重复访问。
- 控制台持续刷异常日志。
- 永久错误永远占用消费者资源。
- 服务重启后只处理新消息，旧 Pending 可能长期得不到处理。

### 优化

- 每个消费者定期扫描属于自己的 Pending List，默认间隔 `5s`。
- 单次读取或基础设施失败后退避 `1s`，避免紧密循环。
- 使用 Redis Hash 记录每条消息重试次数。
- 普通处理失败最多尝试 3 次。
- 达到重试上限后进行 Redis/MySQL 最终一致性检查：
  - MySQL 存在同一个订单 ID：按重复消费处理，恢复 Redis 标记后 ACK。
  - MySQL 已存在不同订单 ID：说明 Redis 标记曾丢失，本次错误订单多扣了一份 Redis 库存；通过 Lua 幂等回补库存，恢复购买标记，并把已有订单 ID 返回给用户。
  - MySQL 不存在订单：写入死信 Stream，状态标记为 `MANUAL_REVIEW`，供人工补偿。
- 必须先成功写入死信或完成补偿，才能 ACK 原消息；一致性检查自身失败时继续保留 Pending。

### 优化后的结果

- 异常消息不会在一个 `while` 循环中立即无限重试。
- 正常消息可以继续处理，不会因为单条永久失败消息阻塞整个消费者。
- 正常压测结束后 `streamPendingFinal = 0`。
- 同订单重复消费不会重复扣 MySQL 库存；不同订单 ID 冲突能够识别并执行一次性 Redis 库存补偿。

## 七、单线程、单条读取和额外锁限制消费能力

### 问题

原消费链路存在多层串行化：

- 单线程消费 Stream。
- 每次 `COUNT 1`，一次只取一条消息。
- 落库前使用 Redisson 用户锁。
- 每条订单先执行一次 `SELECT COUNT`。
- 每条订单单独 INSERT、单独扣减库存。

Redis Consumer Group 已保证一条新消息正常情况下只会分配给组内一个消费者；Lua 已做入口防重，MySQL 还有唯一索引兜底。因此每条订单再获取 Redisson 用户锁属于重复保护，会增加网络往返和锁竞争。

### 优化

- 消费线程数改为 8，每个线程使用独立消费者名。
- Stream 单次读取数量从 1 提升到 100。
- 删除落库阶段的 Redisson 用户锁。
- 删除正常路径中的 `SELECT COUNT`。
- 依靠 Lua 防重、Consumer Group 的消息分配和 MySQL 唯一索引完成幂等保护。

### 优化后的测试结果

固定 10 秒压测结果：

| 并发线程 | QPS | 平均响应 | P99 | 请求结束时 MySQL 订单 | 最终订单 | 消费追平时间 |
|---:|---:|---:|---:|---:|---:|---:|
| 50 | 2,095.2 | 22.8 ms | 45 ms | 4,059 | 20,638 | 51.497 s |
| 100 | 2,109.4 | 45.4 ms | 92 ms | 4,209 | 20,792 | 49.082 s |
| 200 | 2,119.4 | 90.7 ms | 189 ms | 4,204 | 20,751 | 50.499 s |

结论：入口 QPS 已从约 900 提升到约 2,100，但并发从 50 增加到 200 后吞吐量几乎不再增加，只是平均延迟持续升高；同时消费者需要约 50 秒才能追平生产者，说明链路中仍有共享串行瓶颈，而且异步落库明显落后。

## 八、增加 Tomcat 或 Redis 主连接池不能解决串行瓶颈

### 问题与假设

曾推测 Tomcat 线程或 Redis 连接池不足，因此把连接池/并发容量继续放大，期望 QPS 随线程数增加。

### 测试结果

连接池放大后的对照结果：

| 场景 | 并发线程 | QPS | 平均响应 | P99 |
|---|---:|---:|---:|---:|
| 原配置 | 50 | 2,095.2 | 22.8 ms | 45 ms |
| Pool 64 | 50 | 1,978.2 | 24.2 ms | 49 ms |
| 原配置 | 100 | 2,109.4 | 45.4 ms | 92 ms |
| Pool 64 | 100 | 2,097.5 | 45.7 ms | 94 ms |

增加连接数没有带来吞吐量提升。更多线程只会在同一个串行点前排队，因此 QPS 不变、等待时间变长。

### 优化决策

- 不再盲目增加 Tomcat 线程数。
- 主 Redis Lettuce 池保留合理容量，后续通过分段诊断定位真正的串行点。
- Redis 集群和更多 Tomcat 实例暂不作为第一优先级，因为当时 Redis CPU 和应用 CPU 都没有耗尽，单纯横向扩容会掩盖单实例代码锁竞争。

## 九、Lua 脚本资源检查锁是入口 QPS 的核心瓶颈

### 问题定位

为了定位约 2,100 QPS 的平台期，将请求链路逐段拆开进行相同的 100 线程、10 秒诊断：

| 诊断接口 | 主要逻辑 | JMeter 吞吐量 |
|---|---|---:|
| No-op | 仅返回固定响应 | 58,731.6 req/s |
| ID | 仅生成 Redis ID | 25,923.1 req/s |
| Base GET | 不带鉴权的普通请求 | 21,420.3 req/s |
| Auth GET | 带 Token 鉴权 | 9,983.8 req/s |
| Lua | 执行通过 `setLocation` 加载的 Lua | 1,588.7 req/s |
| ID + Lua | 生成 ID 后执行 Lua | 1,537.9 req/s |
| Lua + 扩大连接池 | Lua，Redis 池继续放大 | 1,586.9 req/s |

隔离结果表明：Tomcat、鉴权、Redis ID 和普通 Redis 请求都能达到远高于 2,100 的吞吐量，只有 Lua 路径骤降到约 1,600，并且扩大连接池没有效果。

在 Lua 压测期间使用 `jstack -l <PID>` 采样，发现大量 Tomcat 工作线程竞争 `ResourceScriptSource.isModified()`。原代码使用：

```java
script.setLocation(new ClassPathResource("seckill.lua"));
```

这并不等于“启动时读取一次后完全复用”。每次执行前仍可能进入资源变更检查；高并发时检查路径中的同步会形成应用内锁竞争。

### 优化

应用启动时一次性读取 Lua 文件内容，并把不可变脚本文本交给 `DefaultRedisScript`：

```java
String scriptText = StreamUtils.copyToString(
        new ClassPathResource(resourceName).getInputStream(),
        StandardCharsets.UTF_8
);
return new DefaultRedisScript<>(scriptText, Long.class);
```

这样运行期直接复用脚本文本和 SHA1，不再检查 classpath 文件是否发生变化。

### 优化后的测试结果

相同诊断接口改用脚本文本后：

- Lua 诊断吞吐量：`1,588.7 -> 22,454.9 req/s`
- 提升约 `14.1 倍`

真实秒杀接口使用 100 线程、持续 5 秒：

- 成功请求：32,016
- 错误：0
- QPS：`6,654.7`
- 平均响应：`13.7 ms`
- P99：`26 ms`
- 请求结束时 MySQL 只有 2,260 条订单
- 最终消费完成耗时：`91.792 s`

入口瓶颈被解除后，生产速度显著提高，新的主要瓶颈转移到了 Stream 消费和 MySQL 落库阶段。

## 十、逐条落库和库存热点行导致消费者严重积压

### 问题

入口达到 6,654.7 QPS 后，32,016 条消息在请求结束时只有 2,260 条完成落库，消费者还需要 91.792 秒才能追平。主要原因是：

- 每条订单单独 INSERT。
- 每条订单单独更新同一条 `tb_seckill_voucher` 库存记录，热点行被频繁加锁。
- 每条订单单独开启事务、提交事务和 ACK。
- 即使 Stream 一次读取多条，数据库仍按单条执行，批量读取没有转化为批量落库收益。

### 优化

- Stream 每批最多读取 100 条。
- 按 `voucherId` 对订单分组。
- 每种券执行一次批量 `INSERT IGNORE`。
- 根据真实插入条数执行一次：

```sql
UPDATE tb_seckill_voucher
SET stock = stock - :inserted
WHERE voucher_id = :voucherId
  AND stock >= :inserted;
```

- JDBC 开启 `rewriteBatchedStatements=true` 和预编译缓存。
- Hikari 最大连接数设置为 16、最小空闲连接为 8，与 8 个消费者匹配。
- 成功状态使用 Redis Pipeline 批量写入；整批事务和状态发布成功后批量 ACK。

### 优化后的测试结果

100 线程、持续 5 秒：

- 成功请求：35,321
- 错误：0
- QPS：`7,331.1`
- 平均响应：`12.4 ms`
- P99：`22 ms`
- 请求结束时 MySQL 订单：35,321
- 消费追平时间：`0 s`
- MySQL 库存：64,679
- Redis 库存：64,679
- Pending：0

与 Lua 加载优化后的单条落库版本相比：

- 入口 QPS 提升约 `10.2%`。
- 最关键的是消费者追平时间从 `91.792 s` 降为 `0 s`，生产者和消费者已经基本同步。

## 十一、批量落库中一条失败可能拖垮整批

### 问题

批量 100 条虽然提升吞吐量，但如果其中一条消息异常，存在两个错误方向：

1. 整批直接 ACK：失败消息会永久丢失，造成 Redis 已扣库存但 MySQL 没有订单。
2. 整批长期重试或立即全部退化为单条：一条永久异常会让整个批次吞吐量骤降。

### 优化

- 对异常分类：
  - 数据库连接异常、事务死锁/回滚、库存整体不一致属于批次级故障，整批保留 Pending 并退避，不做二分，避免放大数据库故障。
  - 唯一键或订单 ID 冲突属于可隔离的数据级故障，通过二分拆批定位异常记录，正常子批次继续提交和 ACK。
- 正常批次不会执行额外查询；只有 `INSERT IGNORE` 忽略了记录时，才查询并核对数据库中的真实订单 ID。
- 同一订单 ID 属于消息重复消费：不重复 INSERT、不补偿库存、直接按幂等成功处理。
- 不同订单 ID 属于错误重复下单：幂等回补 Redis 库存，恢复已购标记，返回原订单 ID。
- ACK 始终发生在对应子批次事务提交、最终状态写入或死信/补偿完成之后。

### 优化后的测试结果

加入失败隔离逻辑后，对正常路径再次执行 100 线程、持续 5 秒测试：

- 成功请求：32,763
- 错误：0
- QPS：`6,868.6`
- 平均响应：`13.3 ms`
- P99：`24 ms`
- 请求结束时 MySQL 已有全部 32,763 条订单
- 消费追平时间：`0.001 s`
- Redis/MySQL 库存一致
- Pending：0

失败隔离增加了健壮性，正常路径仍保持约 6,900 QPS，并且消费者能够实时追平。

## 十二、前端“请求受理成功”不等于订单最终创建成功

### 问题

Lua 返回 0 时，只能说明库存预扣和消息入队成功。若接口直接向前端返回“购买成功”，而消费者随后落库失败，用户会看到成功提示，但数据库中没有订单。

不同订单 ID 冲突尤其容易造成误解：用户第二次请求被 Redis 受理并获得了新订单 ID，但数据库中真实有效的是之前的订单 ID。

### 优化

增加异步订单状态机：

- `PROCESSING`：Lua 已受理，请求正在异步处理。
- `SUCCESS`：MySQL 事务已提交。
- `DUPLICATE_EXISTING`：数据库已存在另一真实订单，返回 `existingOrderId`。
- `MANUAL_REVIEW`：重试和最终一致性校验后仍无法自动完成，已进入死信等待人工处理。

接口返回 `PROCESSING + orderId`，前端通过状态查询接口轮询最终结果。状态 Key 保留 1 天，过期后仍可使用 MySQL 订单兜底查询；查询时校验订单所属用户，避免越权查看。

### 优化后的测试结果

最终稳定测试使用 200 线程、持续 10 秒：

- 样本数：84,311
- 成功：84,311
- 错误：0
- QPS：`8,674.9`
- 平均响应：`22.1 ms`
- P90：`31 ms`
- P95：`37 ms`
- P99：`48 ms`
- 最大响应：`66 ms`
- 请求结束时 MySQL 订单：84,311
- 最终 MySQL 订单：84,311
- MySQL 去重用户：84,311
- MySQL 库存：15,689
- Redis 库存：15,689
- Pending：0

300 和 400 并发、5 秒突发测试分别出现 57 和 37 个连接建立失败，错误均为 `HttpHostConnectException`，而不是业务响应失败。200 并发持续 10 秒时错误为 0，说明当前单实例稳定工作点约在 200 并发；更高突发并发仍需单独测试监听队列、连接建立和压测机端口等入口条件。

## 十三、Stream 阻塞读取占用主 Redis 连接池

### 问题

`XREADGROUP BLOCK 2000` 在等待消息期间会独占 Redis 连接。8 个消费者长期阻塞读取时，如果与秒杀 Lua、订单状态、ACK 和普通缓存共用同一个 Lettuce 池，就会挤占接口请求连接。

连接池不是无限的。继续增加主池容量虽然可以延缓耗尽，但不能隔离阻塞消费者和在线请求，故障时两条链路仍会相互影响。

### 优化

- 新建仅供 Stream 读取使用的独立 `LettuceConnectionFactory`。
- 用 `SeckillStreamReader` 封装专用 `StringRedisTemplate`，不把第二个 `RedisConnectionFactory` 直接注册成普通 Spring Bean，避免 Spring Boot 主 Redis 自动配置回退。
- 新消息读取和 Pending 读取均使用专用读取器。
- 独立池配置：
  - `maxTotal = 12`
  - `maxIdle = 12`
  - `minIdle = 8`
  - 命令超时 `5s`，高于 `BLOCK 2s`
  - 客户端名称 `hmdp-seckill-stream-reader`
- Lua、状态查询、ACK、重试计数、死信和普通缓存继续使用主连接池。
- 启动时校验独立池最大连接数不能小于消费者线程数。

### 优化后的验证结果

本次修改后尚未重新执行完整 QPS 对照压测，但运行时 `CLIENT LIST` 已验证连接隔离生效：

- 8 条客户端名称为 `hmdp-seckill-stream-reader` 的连接处于 `flags=b`。
- 8 条阻塞连接当前命令均为 `xreadgroup`，与 8 个消费者线程一一对应。
- 另有 1 条该独立工厂的非阻塞共享连接。
- 主业务 Redis 连接不再承担 Stream 阻塞读取。

## 十四、当前暂未实施的优化

### 1. Stream 长度治理

`XACK` 只会把消息从 Pending List 中移除，不会删除 Stream 中的消息。当前尚未引入 `MAXLEN`、`XTRIM` 或归档策略，Stream 仍会随历史订单持续增长。

后续应根据故障恢复窗口和审计要求设计安全裁剪，不能只为了节省内存直接删除可能尚未处理的消息。

### 2. Redis 集群

最终稳定测试中 Redis 平均约 `130,627 ops/s`，Redis CPU 消耗约 `5.28s / 9.719s = 0.54` 个核心，当前首要瓶颈并不是 Redis 单线程执行能力，因此暂未引入 Redis Cluster。

未来如果引入 Cluster，需要注意 Lua 涉及的多个 Key 必须使用相同 Hash Tag 才能落到同一 Slot；当前独立 Stream 连接工厂也需要改为 Cluster 配置，而不是单机配置。

### 3. Tomcat/Nginx 横向扩容

单纯把线程池扩大到 64 已证明没有收益。当前单实例稳定测试已经达到约 8,675 QPS，下一步应先在独立压测机上重新测试入口连接上限，再决定是否通过 Nginx 增加 Tomcat 实例。横向扩容时仍需监控共享 MySQL 热点行和 Redis 总吞吐量。
