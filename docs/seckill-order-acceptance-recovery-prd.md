# 秒杀订单受理、异常恢复与只读对账 PRD

> 版本：v1.1（核心链路已实现；D1、D2 待业务决策）  
> 适用范围：当前 `redis-handoff` 秒杀订单链路  
> 参考材料：用户提供的《秒杀系统 PRD：一人一单与对账补偿》及本项目现有实现

## 1. 背景与产品决策

当前请求在 Redis Lua 中完成库存预扣、用户已购标记和 Handoff 写入后，默认模式立即返回 `SUCCESS / 抢券成功`。此时 MySQL 订单尚未创建。该响应把“资格已锁定”和“订单已创建”混为一谈。

本 PRD 将两者分开：**Lua 预扣成功表示受理成功，返回 `PROCESSING` 和预先生成的 `orderId`；只有 MySQL 订单事务提交后才返回 `SUCCESS`。** 用户可用 `orderId` 查询最终结果，推送可作为补充渠道。

预扣成功后的 Redis 记录是对用户已受理事实的证据。MySQL 订单是最终落库事实，Outbox 是中间持久化和投递记录。MySQL 库存因异步处理而滞后时，不得仅依据库存差额覆盖 Redis 预留或已购集合。

### 1.1 目标

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| G1 | 返回准确状态 | Lua 成功后返回 `orderId + PROCESSING`；订单事务提交后才显示 `SUCCESS` |
| G2 | 一人一笔有效订单 | 同一用户、同一活动在任一时刻最多持有一笔未取消订单；取消后的再次购买按现有业务规则允许 |
| G3 | 不超卖、不重复扣库 | 有效订单不超过可售额度；同一 `orderId` 的重复消息不重复建单或扣 MySQL 库存 |
| G4 | 已受理任务可追踪 | 每笔已返回 `PROCESSING` 的请求可按 `orderId` 查询，并能追踪到 Handoff、Outbox、订单或明确的人工处理记录 |
| G5 | 卡单可发现、可恢复 | 超过处理时限的任务被告警并推进补单；超时或进入死信本身不触发库存回补 |
| G6 | 对账不改变已受理事实 | 定时审计只读；不会因为 MySQL 库存滞后而自动重写 Redis 库存或已购集合 |

### 1.2 非目标

- 本期不覆盖支付、履约、退款和营销赔付规则。
- 不要求 Redis 与 MySQL 库存在活动进行时数值相等。
- 不以定时任务自动判定一笔已受理订单为失败。
- 不通过 Kafka 的生产者幂等配置宣称跨 MySQL、Redis 和 Kafka 的端到端“只执行一次”。

## 2. 现状与差距

| 项目现状 | 本 PRD 要求 |
| --- | --- |
| 默认 `redis-handoff` 模式下，Lua 成功直接返回 `SUCCESS` | 返回 `PROCESSING`；`SUCCESS` 仅由已提交订单确认 |
| Lua 原子预扣并写 Handoff；后台转存 Outbox | 保留该交接路径，按原 `orderId` 幂等重试 |
| Outbox 状态包括 `PENDING`、`SENT`、`COMPLETED`、`MANUAL_REVIEW` | 沿用现有状态；明确用户状态与内部投递状态的映射 |
| DLT 消费者自动重新入队；`MANUAL_REVIEW` 也会定时重试 | 连续不可恢复的任务应进入可告警、可人工接管的稳定状态，不能无限无感循环 |
| 定时 `SeckillOrderReconciliationService` 以 MySQL 库存及待处理数重写 Redis 库存和已购集合 | 停用自动重写，改为逐单巡检与只读库存审计 |
| 订单表只有 `id` 主键；为允许取消后重购，已移除 `(user_id, voucher_id)` 唯一索引 | 保留取消后重购语义；评审数据库层“同一时刻一笔有效订单”的兜底约束 |
| 重复消息核验用只查询未取消订单的方法 | 改为按 `orderId` 查询历史订单并核对用户、券，避免取消后的迟到消息反复重试 |
| 状态查询先访问 MySQL，再访问 Redis 凭证 | MySQL 不可用且 Redis 受理凭证存在时，仍返回 `PROCESSING` |
| Handoff 转存 Outbox 时立即删除 Redis 受理凭证 | 若要求 MySQL 故障期间仍可查状态，凭证需保留到终态可查询，并设置有界的终态保留期 |

## 3. 用户状态与承诺边界

| 用户状态 | 判定依据 | 用户文案 | 是否终态 |
| --- | --- | --- | --- |
| `PROCESSING` | Lua 预扣成功，Handoff 或受理凭证存在；订单尚未确认提交 | 资格已锁定，订单处理中 | 否 |
| `MANUAL_REVIEW` | 自动恢复暂时无法推进，需要人工核查；预留仍有效 | 订单处理异常，正在核查 | 否 |
| `SUCCESS` | 对应 `orderId` 的 MySQL 订单事务已提交 | 订单创建成功 | 是，后续可进入取消等订单业务状态 |
| `FAILED` | 经明确终态决策，确认没有订单或在途处理，预留已幂等释放 | 抢购未完成，资格已释放 | 是 |
| `CANCELLED` | 已成功创建的订单按取消流程完成 | 订单已取消 | 是 |
| `UNKNOWN` | 数据源暂时不可判定，不能证明未受理 | 结果暂未确认，请稍后按订单号查询 | 否 |

允许的主要流转为 `PROCESSING → SUCCESS`，或 `PROCESSING → MANUAL_REVIEW → SUCCESS`。`FAILED` 只允许经过 FR-6 的终态决策和释放流程产生。超时、Kafka lag、死信和 MySQL 短暂不可用都不是 `FAILED` 的充分条件。已显示 `SUCCESS` 的订单不得因异步消息迟到而改成 `FAILED`；用户主动取消走 `CANCELLED`。

接口的 `Result.ok` 仅表示本次受理请求成功，不能替代订单状态。前端按钮和通知必须依据 `status` 展示，不得仅依据 HTTP 2xx 或 `Result.ok` 展示“订单已创建”。

## 4. 核心流程

1. 服务端在执行 Lua 前生成 `orderId`。
2. Lua 原子检查活动、库存、一人一单和资格令牌；成功时扣 Redis 库存、加入已购集合，并写入 Handoff 与受理凭证。
3. API 返回 `orderId`、`PROCESSING` 和“资格已锁定，订单处理中”。如果 Lua 执行结果不确定，返回 `UNKNOWN`，不得声称已受理或明确失败。
4. Handoff Relay 批量幂等写 MySQL Outbox；**确认事务提交后**才移除 Redis Handoff。
5. Outbox Relay 按租约领取事件，发送 Kafka。发送结果不确定时允许重发；`SENT` 仍需重查直至消费完成。
6. Kafka 消费者在事务中按 `orderId` 幂等插单，仅按实际新增订单数扣 MySQL 库存，同时将 Outbox 标记完成；事务提交后手动 ACK。
7. 状态查询或推送在订单提交后向用户呈现 `SUCCESS`。失败消息进入重试、死信或人工核查流程，不因重试耗尽而自动返还预留。

全链路的重投、补单、查询和终态处理沿用首次生成的 `orderId`。Kafka 消息 key 沿用当前实现的 `voucherId`，以保持同一券的分区策略；本期不要求跨券顺序。

## 5. 功能需求

### FR-1 受理接口与一人一单（P0）

- 保留 Redis Lua 的原子边界：库存和已购检查、资格令牌校验与消费、预扣、已购集合写入、Handoff 和受理凭证写入必须作为一次脚本执行。
- 同一用户对同一券的并发请求最多一次 Lua 返回成功。失败请求不创建 Handoff，也不消耗 MySQL 库存；跳过的订单 ID 无需复用。
- 返回 `PROCESSING` 时包含首次 `orderId`，文案为“资格已锁定，订单处理中”。接口重试不得产生第二笔成功预留。
- 取消后的再次购买沿用现有规则；数据库侧的有效订单唯一性方案必须允许保留多笔已取消的历史订单。
- Redis 预扣成功但 API 响应丢失时，用户应能用已获得的 `orderId` 查询；若用户没有收到 `orderId`，需提供按用户和券查询当前有效受理的能力，不能只依赖已落库订单查询。

### FR-2 可靠交接与 Outbox（P0）

- Handoff 与受理凭证应保留 `orderId`、`userId`、`voucherId` 和受理时间，支持崩溃后恢复、归属校验及超龄巡检。
- Outbox 以 `orderId` 和稳定事件 ID 去重。重复插入必须核对订单、用户、券和来源字段；冲突进入告警及人工核查。
- Redis Handoff 只在相应 Outbox 事务确认提交后删除。若删除前崩溃，重启后再次写入应得到同一条事件。
- Outbox Relay 失败时按既有租约和退避机制重试；Publisher 成功发送但未标记 `SENT` 时允许重发。
- 若要求 MySQL 故障期间仍可查询 `PROCESSING`，受理凭证必须保留到终态已记录且过了约定的查询保留期；清理须有边界和容量控制，不能在 Outbox 提交后立即删除。任何清理操作不能导致查询出现“已受理但无状态”的空窗。

### FR-3 消费落库与 ACK（P0）

- Consumer 与事务服务位于不同 Spring Bean，确保事务经代理生效；Listener 在事务服务成功返回后手动 ACK。
- 同一批消息先按 `orderId` 去重；订单插入和 MySQL 库存扣减处于同一事务，扣减量为实际新插入的订单数。
- 插入被忽略时按 `orderId` 主键查历史订单，核对 `userId`、`voucherId`；已取消订单对应的迟到重复消息也应作为已处理消息确认，不再扣库存。
- 库存扣减失败或字段冲突必须抛出事务边界，不得在事务方法内捕获后正常返回。
- 消费完成后 Outbox 变为 `COMPLETED`；重复消费不重复建单、不重复扣 MySQL 库存，也不反复进入重试。

### FR-4 死信与人工接管（P0）

- 可恢复的系统异常按退避策略重试。达到自动重试上限时进入死信并告警，但死信**不是最终失败状态**。
- 死信处理先按 `orderId` 查订单：已有订单则补齐 Outbox 完成状态；没有订单则按明确策略补单或进入 `MANUAL_REVIEW`。
- `MANUAL_REVIEW` 必须是可观测、可暂停自动重试的稳定停车状态，保留库存预留，并记录失败原因、操作历史、下一责任人和处理截止时间。
- 人工动作至少支持：按原 `orderId` 重试、确认订单已完成、发起终态失败审核；动作需记录操作人、原因和时间。
- 不得把“超过重试次数”“进入死信”或“人工核查中”直接解释为可回补库存。

### FR-5 超时巡检与向前恢复（P0）

- 定时巡检按 `orderId` 扫描超龄 Handoff、未完成 Outbox、死信及人工处理任务；任务可重复执行且多实例互斥或按租约领取。
- 判断顺序：① 订单已存在则补齐完成状态并清理残留；② 无 Outbox 但有可信 Redis 受理记录则补写 Outbox；③ Outbox 待投递则按既有退避继续；④ 已投递未落单则核对消费者进度、重投或人工接管。
- 超时阈值只决定重查、重投、告警和升级人工，不决定自动 `FAILED` 或库存回补。阈值应依据实际 P99 处理时长、Kafka lag 和最大重试窗口校准。
- 当前没有逐笔 Consumer 处理租约或心跳，无法仅凭 `SENT` 与订单缺失证明消费者已失败。本期至少要保证超时只触发可逆的重投与告警；若要自动判断消费者卡死，需另行增加逐单处理租约及栅栏。
- 已受理但 Handoff、Outbox 和订单均缺失的情况属于高优先级异常。若受理凭证仍在，先用原 `orderId` 恢复；证据不完整时不得猜测并释放库存。

### FR-6 终态失败与预留释放（P0，受控动作）

- 本期默认策略为**向前补单优先**。只有经明确业务规则或人工审核确认不能履约，才允许从 `PROCESSING` / `MANUAL_REVIEW` 转为 `FAILED`。
- 终态决策前必须按 `orderId` 再查订单、Outbox、Handoff 和在途消费者；订单已存在时禁止释放。终态决策与消费者落库必须通过同一订单维度的数据库栅栏或行锁串行化，阻止补偿后迟到消息建单。
- 释放动作以 `orderId` 幂等：持久化失败决策，使用一次性补偿标记执行 Lua；仅当本次确实移除了该用户预留时回补 Redis 库存，同时清理对应 Handoff 和受理凭证。宕机重试不得再次加库存。
- 只有释放完成并记录成功后，才对用户展示 `FAILED`，并记录原因、时间、操作方；用户通知与赔付策略由产品、运营另行确认。
- 用户主动取消已创建订单继续走独立的取消流程，不复用“受理后未落库失败”的处理规则。

### FR-7 状态查询与通知（P0）

- 只允许订单所属用户按 `orderId` 查询。订单存在时返回 `SUCCESS` 或已取消状态；Outbox、Handoff 或受理凭证存在时返回 `PROCESSING`；人工停车记录返回 `MANUAL_REVIEW`；已完成失败决策及释放返回 `FAILED`。
- MySQL 查询失败时若 Redis 受理凭证存在，仍返回 `PROCESSING`；若两侧均无法确认，返回 `UNKNOWN`，不得直接返回“未抢到”。这一目标依赖 FR-2 将凭证保留到终态；若不采用该保留策略，必须明确降级为 `UNKNOWN`。
- 推送只用于缩短用户等待，不是唯一事实来源；前端需支持轮询，直至终态或展示人工核查提示。

### FR-8 只读对账与监控（P1）

- 将现有定时自动重建 Redis 库存及已购集合改为**只读审计和告警**。审计可以计算 MySQL 库存、已落单订单、Handoff 和未落单 Outbox 的关系，但不得据此自动覆盖 Redis。
- 活动进行中，MySQL 与 Redis 库存差额可由在途预留解释，不得因数值不相等报警或回补。无法由可追踪受理记录解释的差额应告警并保留证据。
- 活动结束、无在途处理且订单与取消流程稳定后，核对活动额度、有效订单、Redis 剩余库存与已购集合；异常进入人工核查，不自动改写已受理事实。
- Redis 丢失数据属于灾难恢复事件，需要从足够完整的受理流水恢复；如果受理流水和待落库任务同时丢失，仅凭 MySQL 库存无法还原已回复用户的资格。

## 6. 数据与接口约束

| 对象 | 当前形态 | 本期关键约束 |
| --- | --- | --- |
| Redis 库存 / 已购集合 | `seckill:stock:<voucherId>`、`seckill:order:<voucherId>` | Lua 原子变更；不得由定时对账自动覆盖 |
| Redis Handoff | `seckill:order:handoff:{<voucherId>}`，成员含 `orderId|userId|autoIssued` | 补齐可可靠获取的受理时间；Outbox 提交后才清理 |
| Redis 受理凭证 | `seckill:order:accepted` Hash，field 为 `orderId` | 需支持查询归属及受理时间；若要实现 MySQL 故障期间的状态查询，保留到终态可查询及约定保留期，按容量设计清理 |
| MySQL Outbox | `tb_seckill_order_outbox`，`order_id`、`event_id` 唯一 | 记录重试、最近错误、投递状态及人工处理轨迹 |
| MySQL 订单 | `tb_voucher_order.id = orderId` | 主键防同订单重复；评审“未取消订单唯一”兜底约束 |
| 终态处理记录 | 当前缺少独立的失败决策和补偿流水 | 在启用 `FAILED` 前补齐按 `orderId` 唯一的决策、执行状态和审计字段 |

建议受理接口响应示例：

```json
{
  "orderId": 4611686018427387904,
  "status": "PROCESSING",
  "message": "资格已锁定，订单处理中"
}
```

状态查询应返回同一 `orderId`、当前用户状态、更新时间及可展示原因。前端不得将一次请求成功与订单最终成功等同。

## 7. 监控与处理时限

| 指标 | 触发后的动作 |
| --- | --- |
| Handoff 最老年龄、转存失败数 | 检查 Relay 与 MySQL；按原 `orderId` 补写 Outbox |
| Outbox `PENDING` / `SENT` 最老年龄、重试次数 | 检查投递租约、Kafka 状态和订单；重投或转人工 |
| Kafka lag、DLT 积压 | 告警并扩容或排障；不按积压时长自动释放预留 |
| `MANUAL_REVIEW` 数量与最老年龄 | 指派责任人、记录处理结果和处理时限 |
| `PROCESSING → SUCCESS` 耗时分位数 | 校准巡检告警阈值和用户端提示 |
| 无法解释的库存差额、受理凭证孤儿记录 | 高优先级调查，不自动调整 Redis |
| 终态失败与补偿执行次数 | 按原因聚合、审计和复盘 |

巡检频率与超时阈值由压测及线上分位数确定。可先以分钟级巡检、分级告警上线；任何“超过 N 分钟直接补偿”的规则均不在本 PRD 范围内。

## 8. 验收场景

1. 库存 100、同用户高并发点击：Lua 成功最多一次；成功响应为 `PROCESSING + orderId`，未落库前不显示“订单创建成功”。
2. Lua 成功后 MySQL 故障：Handoff 保留，查询返回 `PROCESSING`；MySQL 恢复后以同一 `orderId` 落库并变为 `SUCCESS`。
3. Outbox 提交后、删除 Handoff 前宕机：重启重复转存不生成第二条 Outbox。
4. Kafka 发送成功后、标记 `SENT` 前宕机：重发后仅创建一笔订单、仅扣一次 MySQL 库存。
5. 消费事务提交后、Kafka ACK 前宕机：重复消费正常 ACK，库存不重复扣；原订单已取消时也不会因历史查询条件而陷入重试。
6. Kafka 消费长期失败或进入 DLT：用户看到 `PROCESSING` 或 `MANUAL_REVIEW`；预留不因超时自动释放，人工可按原 `orderId` 补单。
7. MySQL 不可用时查询已受理 `orderId`：Redis 受理凭证仍能证明资格，返回 `PROCESSING`；不能确认时返回 `UNKNOWN`。
8. 人为制造 Redis 与 MySQL 数值差额：若差额可由在途任务解释，不触发库存改写；无法解释则告警并保留现场。
9. 明确终态失败且无在途处理：故障注入覆盖失败决策、Redis 释放和状态写回之间的每个崩溃点；重试后只释放一次，迟到消息不能建单。
10. 用户主动取消后再次购买：历史已取消订单保留，新受理允许；重复的旧 Kafka 消息不会干扰新订单。

## 9. 上线顺序与回滚

1. **语义改造**：API 返回 `PROCESSING`；修复状态查询在 MySQL 故障时的降级；前端调整文案和状态轮询。
2. **幂等与恢复**：修复取消后迟到重复消息的核验；完善 Handoff、Outbox、DLT 的逐单巡检和告警。
3. **人工停车**：将连续失败任务置于稳定的 `MANUAL_REVIEW`，提供补单与终态审核入口；未完成审核前不释放预留。
4. **只读对账**：停用现有定时 Redis 覆盖任务，先以只读审计观察一个活动周期，再决定是否保留灾难恢复专用的人工触发重建工具。
5. **受控失败流程**：只有第 10 节的业务规则与可靠性前提确定后，才灰度启用终态失败和库存释放。

出现异常时，可关闭自动重投或终态失败入口，但不能丢弃已受理任务；用户查询与人工接管继续可用。

## 10. 待评审决策与上线门槛

| 编号 | 决策 | 原因与建议 |
| --- | --- | --- |
| D1 | Redis-only 受理的持久化等级与可接受丢失窗口 | 当前默认模式在 MySQL Outbox 提交前就回复成功。若要求“已回复 `PROCESSING` 的受理绝不丢失”，必须证明回复前已有足够持久的受理凭证；否则改为 Outbox 确认提交后回复，或明确接受并披露风险。定时对账无法补回两侧都丢失的受理事实。 |
| D2 | 哪些不可履约情形允许最终 `FAILED` | 超时、DLT 和暂时库存不一致均不自动构成失败。需由产品与运营明确最终决策、通知和赔付规则。 |
| D3 | 数据库层的一人一笔有效订单约束 | 当前 `(user_id, voucher_id)` 唯一索引已移除以支持取消后重购；应评审仅约束未取消订单的数据库方案。 |
| D4 | `MANUAL_REVIEW` 的人工处理时限、责任人与入口 | 当前状态会自动重新入队；需明确何时停止自动重试、谁接管、如何审计。 |
| D5 | 用户结果通知渠道 | 订单查询是必备渠道；站内信、短信或 App 推送及失败赔付另行确定。 |

**发布门槛：**D1 必须有明确选择，不能同时宣称“Redis-only 立即回复”与“任何 Redis 故障下受理零丢失”；D2 未确定前只上线补单、人工核查和告警，不上线自动 `FAILED` 与库存释放。

## 11. 实现与自测记录

- 已实现：`PROCESSING + orderId` 受理响应、受理凭证保留和终态清理、MySQL 故障时 Redis 状态降级、按用户和券查在途订单号、逐单租约巡检及原单号补写 Outbox。
- 已实现：按订单主键验证重复消费，包括取消后的迟到消息；MySQL 有效订单唯一约束；Kafka 事务提交后手动 ACK；死信停车为 `MANUAL_REVIEW`，停止定时自动重试。
- 已实现：人工任务列表、人工重试、核实已完成、发起终态失败审核申请，操作均记录操作人、原因和时间；超时任务由定时巡检记录错误告警。失败审核申请不产生 `FAILED`，也不释放预留。停车任务默认指派 `seckill-ops` 队列，1 小时处理时限，具体人员和 SLA 仍待 D4 确认。
