商户查询：双重缓存、Redisson
与缓存穿透/击穿治理

目标不是背出 Caffeine、Bloom Filter、Redis 和 Redisson，而是能解释：每一层删掉之后会出现什么问题；为什么它被放在这里；真实代码如何让它们协作。

阅读路径： 1. 先明确目标2. 双重缓存效果3. 为什么 Caffeine4. 总入口代码5. Bloom6. Redis7. Redisson8. L1 失效全链路9. 一致性10. 面试表达

1. 先从问题出发：一条读请求真正怕什么？

接口是 GET /shop/{id}。热门商户会被反复读取，且请求可能来自多个应用实例。若每次都查 MySQL，数据库既承担热点读，又会在缓存失效或恶意 ID 下被突发流量击穿。

请求→Caffeine L1→Bloom Filter→Redis L2→Redisson 重建锁→MySQL

业务目标

让绝大多数热门查询在应用内完成；缓存未命中时也只让极少数请求回源数据库。

正确性目标

不存在的商户不反复穿透；热点 Key 失效时不并发打库；更新后各实例的 L1 不长期陈旧。

重要边界：本项目的缓存是读性能优化，不是最终数据源。缓存暂时失效时应允许回源；不能因为防护组件异常就把真实存在的商户误判为不存在。

2. 为什么要双重缓存：使用前后到底改变了什么？

方案热门 Key 的请求路径主要代价适用结论
无缓存应用 → MySQL每次网络/SQL/连接池开销都落在数据库；热点会直接放大 DB 压力。不适合读多写少的商户详情。
仅 Redis应用 → Redis数据库被保护，但所有命中都要一次网络往返；超热点集中到 Redis。共享缓存层必要，但仍有进一步降压空间。
Caffeine + Redis应用 → 本 JVM；L1 未命中才到 Redis需要处理多实例 L1 的失效通知；允许短暂最终一致。本项目采用：读多、热点明显、可容忍短暂缓存陈旧。

2.1 L1 Caffeine 做什么

它是进程内缓存：无网络、无序列化，命中时最快。代价是每个 JVM 都有自己的副本，因此它不能取代 Redis 的共享缓存角色。

// ShopLocalCache.java：L1 的大小和生命周期
this.cache = Caffeine.newBuilder()
        .maximumSize(maximumSize)                       // 默认 10,000
        .expireAfterWrite(expireAfterWriteSeconds, TimeUnit.SECONDS) // 默认 60 秒
        .build();

public Shop get(Long shopId) {
    return !enabled || shopId == null ? null : cache.getIfPresent(shopId);
}

2.2 L2 Redis 做什么

Redis 是跨 JVM 共享的缓存。某实例回源并写入 Redis 后，其他实例的下一次 L1 未命中可以直接复用；它也是空值标记与分布式锁的共同基础。

效果不是简单叠加两份缓存。L1 把“同一实例的热点重复读”截在本机；L2 把“多个实例之间的缓存数据”共享起来。两层分别优化 CPU/网络路径与跨实例复用率。
关于效果数据：代码配置能确认 L1 默认 60 秒、最大 10,000 条，Redis 默认 TTL 30 分钟；但仓库没有提供该接口的压测结果。因此这里不虚构“QPS 提升/延迟降低”的数值。要量化效果，应对比 L1 命中率、Redis QPS、MySQL 查询次数和 P95/P99 延迟。

3. 为什么已有 Redis，还要加 Caffeine？

因为 Redis 虽然快，但对应用来说仍是远程共享服务；Caffeine 是 JVM 堆内的本地缓存。两者不是重复建设，而是在不同位置截断不同类型的成本。

3.1 一次 Redis 命中，仍然不是“零成本”

业务线程→序列化请求→网络往返→Redis 排队/执行→网络返回→JSON 反序列化

即使 Redis 完全健康，以上步骤仍会消耗网络连接、Redis 命令处理能力以及 JSON 编解码 CPU。Caffeine 命中则是进程内的 cache.getIfPresent()：没有网络往返，也没有 Redis JSON 的序列化/反序列化路径。

维度只用 Redis加入 Caffeine 后
热点请求路径每次都跨网络访问 Redis。同一实例已预热的热点直接从 JVM 内存返回。
Redis 压力所有命中请求都是 Redis 命令。L1 命中的请求不会到 Redis，给秒杀、分布式锁等 Redis 关键路径腾出容量。
尾延迟会受网络抖动、连接池等待、Redis 瞬时排队影响。热点读避开这些外部波动；L1 miss 时仍由 Redis 兜底。
数据一致性天然共享同一份 L2 数据。每个 JVM 有副本，必须做失效通知；本项目接受短暂最终一致。

3.2 关键前提：热点访问具有局部性

Caffeine 有价值的前提不是“请求多”，而是“少数商户被反复请求”。例如某个热门店铺在一台应用实例上连续被访问：第一次 L1 miss 后由 Redis/DB 回填；在默认 60 秒 L1 生命周期内，后续同实例请求均不再访问 Redis。若请求永远是不同的随机 ID，L1 命中率低，收益也会很小。

如何正确描述收益：若一个热点商户在某实例的 60 秒窗口内出现 r 次请求，并且首次回填成功，那么理想情况下可省去约 r − 1 次 Redis 读取。真实收益还受 Caffeine 淘汰、多个应用实例的流量分布、主动失效事件影响，因此必须通过命中率而不是主观估计来验证。

3.3 本项目的 Caffeine 配置及其含义

// ShopLocalCache.java：实际项目代码
this.cache = Caffeine.newBuilder()
        .maximumSize(maximumSize)                         // 默认 10,000：给 JVM 内存设上界
        .expireAfterWrite(expireAfterWriteSeconds, TimeUnit.SECONDS) // 默认 60 秒：限制陈旧窗口
        .build();

public Shop get(Long shopId) {
    return !enabled || shopId == null ? null : cache.getIfPresent(shopId);
}

maximumSize(10000) 是防止“缓存越多越好”的误区：本地缓存占用 JVM 堆，必须有容量上限，避免挤压业务对象、引发频繁 GC。expireAfterWrite(60s) 让 L1 不会无限期保留旧值；它是兜底，主动失效才是更新后的主要收敛手段。

3.4 为什么 Caffeine 放在 Bloom Filter 前面？

Bloom Filter 的职责是快速判定可能不存在的 ID；Caffeine 的职责是最快返回已经验证过且最热的商户。对于 L1 命中的真实热点，先查 Caffeine 能连一次 Bloom/Redis 操作都免去。L1 未命中才把请求交给 Bloom 去筛非法 ID，顺序是性能与职责的共同结果。

3.5 它不是免费午餐：什么时候不该加？

适合加入 Caffeine

  • 读多写少，热点明显；
  • 对象体积可控，能为 JVM 设置容量上限；
  • 允许几十秒以内的最终一致，或已有可靠失效通知；
  • Redis 已是共享缓存，但希望降低其热点 QPS。

要谨慎或不用

  • 要求强一致，任何旧读都不可接受；
  • 数据对象很大，复制到每个 JVM 成本过高；
  • 访问极度随机，L1 命中率很低；
  • 没有失效方案，却存在频繁更新。
一句话总结：Redis 解决“多实例共享缓存”，Caffeine 解决“同一实例的极热读”。Caffeine 的核心收益不是替代 Redis，而是用可控的 JVM 内存换取更低的热点读延迟与更低的 Redis QPS；代价是缓存副本和最终一致性治理。

Shop localHit = localCache.get(shopId);
if (localHit != null) return localHit;                  // ① L1

    return firstLookup.shop;
}
if (firstLookup.nullMarker) return null;                // ④ 缓存过的空值

locked = lock.tryLock(rebuildWaitMillis, rebuildLeaseMillis, TimeUnit.MILLISECONDS);
if (!locked) return readLastChance(shopId);             // ⑤ 未抢到锁不直接查库

// ⑥ 拿锁后再次检查 L1 + Redis；确认仍未命中才回源
Shop shop = databaseFallback.apply(shopId);
if (shop == null) { cacheNull(shopId); return null; }
cacheShop(shopId, shop);                                // 写 L2，再写 L1
记忆口诀：本地快读 → Bloom 拦截假 ID → Redis 共享读 → 锁住重建 → MySQL 兜底。锁不是每个请求都拿，只出现在两级缓存都未命中时。

5. Bloom Filter：解决缓存穿透，但它不能证明“存在”

4.1 要解决什么

攻击者或错误客户端持续请求不存在的 shopId。这种请求不会命中正常缓存，最后会不断回源 DB，这就是缓存穿透。空值缓存可以缓解重复 ID；Bloom Filter 则能在大量随机、分散的非法 ID 到达 Redis 之前先拦下它们。

Bloom 返回含义本项目动作
false该 ID 一定不在已加入集合中。直接返回不存在，不查 Redis/MySQL。
true该 ID 可能存在（会有误判）。继续查 Redis，必要时回源 MySQL；绝不据此直接认定存在。
// ShopBloomFilter.java：真实实现使用 Redisson 的 Redis-backed RBloomFilter
public boolean mightContain(Long shopId) {
    if (shopId == null) return false;
    if (!ready) return true;              // 初始化未完成：fail open，继续正常查询
    try {
        return bloomFilter.contains(shopId);
    } catch (RuntimeException e) {
        ready = false;
        return true;                      // Bloom 故障：宁可多查，不能误杀真商户
    }
}

4.2 数据从哪里来，新增店铺怎么办？

// ShopBloomFilterInitializer.java：应用启动时从 DB 装载全部合法 ID
List<Long> shopIds = shops.stream()
        .map(Shop::getId).filter(Objects::nonNull).collect(Collectors.toList());
shopBloomFilter.initialize(shopIds);

// ShopServiceImpl.saveShop()：新增成功后补入 Filter
shopBloomFilter.put(shop.getId());

配置的预估容量为 100000，允许误判率为 0.01。容量和误判率不是“越小越好”：更低误判率需要更多位图内存；插入量明显超过预估时误判率会变差。

常见误区：Bloom Filter 没有删除语义，且只能判断“不存在一定准确、存在可能误判”。它不能替代数据库、Redis 或空值缓存。

        JSONUtil.toJsonStr(shop), redisTtlMinutes, TimeUnit.MINUTES);

// 不存在的商户：用空字符串作标记，默认 120 秒 + 0~30 秒抖动

        nullTtlSeconds + jitterSeconds, TimeUnit.SECONDS);

三个返回状态必须分清

Redis 的值业务解释后续动作
非空 JSON缓存命中反序列化、回填 L1、返回。
空字符串 ""此前已确认 DB 没有该商户返回不存在，不回源。
null真正缓存未命中进入 Redisson 重建流程。
空值缓存 + Bloom 是互补的：Bloom 更适合挡住海量随机非法 ID；空值缓存更适合挡住“同一个不存在 ID 被重复访问”，也能覆盖 Bloom 误判后的一次真实回源结果。

7. 为什么使用 Redisson：它治理的是缓存击穿

6.1 先区分：缓存击穿不是缓存穿透

穿透

请求一个从未存在的 ID。问题是“非法数据一直回源”。解决：Bloom + 空值缓存。

击穿

一个真实的热点 Key 恰好失效，大量并发同时发现 Redis miss。问题是“合法热点同时回源”。解决：互斥重建锁。

6.2 为什么不是 synchronized？

synchronized 只在单个 JVM 生效。部署两个应用实例时，两个 JVM 可以各自获得自己的本地锁，仍可能同时回源 MySQL。这里要的是跨实例的互斥，锁必须放在共享的 Redis 上。

// ShopCacheServiceImpl.java：仅在 L1、L2 都 miss 时才尝试分布式锁
RLock lock = redissonClient.getLock(LOCK_SHOP_KEY + shopId);
boolean locked = lock.tryLock(rebuildWaitMillis, rebuildLeaseMillis,
        TimeUnit.MILLISECONDS);
if (!locked) {
    return readLastChance(shopId); // 再读缓存，不让失败者去查库
}
try {
    // DCL: 获取锁后重新检查 L1 和 L2
    Shop secondLocalHit = localCache.get(shopId);
    if (secondLocalHit != null) return secondLocalHit;
    CacheLookup secondLookup = readRedis(shopId);
    if (secondLookup.shop != null) return secondLookup.shop;
    return databaseFallback.apply(shopId); // 只有胜者可以回源
} finally {
    if (locked && lock.isHeldByCurrentThread()) lock.unlock();
}

6.3 Redisson 带来的效果

  1. 跨实例互斥：同一 shopId 的缓存重建只有一个赢家，其他实例不同时查 DB。
  2. 失败者再读：未拿到锁的线程执行 readLastChance()，等待/读取已经被赢家回填的缓存，而不是退化为“人人查库”。
  3. 双重检查：排队拿锁期间，其他实例可能已完成重建；拿锁后再次检查可避免无意义回源。
  4. 有界等待：默认等待 3 秒、锁租约 10 秒；避免无期限阻塞。等待结束仍没有缓存则抛异常，而不是用大量 DB 回源掩盖故障。
注意：代码显式传了 leaseMillis=10000。这意味着锁最多持有 10 秒；应确保 DB 回源和缓存回填在这个时间预算内。若回源可能超过租约，需要评估看门狗/续期策略或更合理的超时配置。

6.4 这里还有第二类 Redisson 锁

查询方法上的 @CacheConsistencyLock(... READ) 与更新方法上的 WRITE 使用 Redisson 读写锁，目的是在更新店铺与读取/重建缓存之间建立顺序约束；而 queryById 内的 RLock 专门用于缓存未命中的重建互斥。两者不要混为一谈。

8. 更新后 L1 如何失效：Outbox + Kafka 的完整链路

是的，本项目采用的是经典的 本地事务 + Transactional Outbox + 定时 Relay + Kafka 手动 ACK 模式。但要严谨地说，它实现的是至少一次投递/处理，并依赖“删除缓存是幂等操作”来容忍重复；没有任何分布式系统能承诺消息“绝对一定发送且一定只消费一次”。

更新 MySQL 商户→ 同一事务写 Outbox: PENDING→ 提交后快删本机/L2每 200ms Relay→Kafka→ 每 JVM 独立消费组删本机 L1 + Redis L2→ 手动 ACK

8.2 当前实例的“快路径”：提交后立即删 L1 与 L2

// publish()：只能在事务真正提交后做快删，不能在提交前删
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        invalidationHandler.evictBestEffort(shopId);
    }
});

// ShopCacheInvalidationHandler.evict()
shopLocalCache.invalidate(shopId);                 // 当前 JVM 的 Caffeine L1
stringRedisTemplate.delete(CACHE_SHOP_KEY + shopId); // Redis L2

这是低延迟优化，不是可靠性的唯一依靠。即使这里 Redis 删除失败或应用刚提交就崩溃，Outbox 中的事件仍在，后续 Kafka 广播会重试清理。之所以放在 afterCommit()，是为了避免数据库最终回滚、缓存却被提前删掉。

8.3 Relay：扫描 PENDING，确认 Kafka 接收后才标记 SENT

// ShopCacheInvalidationOutboxRelay：默认每 200ms 执行
@Scheduled(fixedDelayString = "${hmdp.kafka.shop-cache.outbox.poll-delay-ms:200}")
public void relayPending() {
    RLock relayLock = redissonClient.getLock(LOCK_SHOP_CACHE_OUTBOX_RELAY);
    if (!relayLock.tryLock()) return;        // 多实例只有一台 Relay 扫描
    List<ShopCacheInvalidationOutboxEvent> events = outboxMapper.findDispatchable(batchSize);
    for (ShopCacheInvalidationOutboxEvent event : events) dispatch(event);
}

// SQL 只选到期的 PENDING 事件
SELECT ... FROM tb_shop_cache_invalidation_outbox
WHERE status = 'PENDING' AND next_retry_time <= NOW()
ORDER BY id ASC LIMIT #{limit};

outboxMapper.markSent(event.getId());

使用 shopId 作为 key，使同一商户的多次失效事件路由到同一分区，保持分区内顺序。生产者配置了 acks=all 和 enable.idempotence=true：前者要求 ISR 副本确认，后者避免生产端重试把同一发送重复写入 Kafka。

仍可能重复，且这是预期设计：若 Kafka 已确认消息，但应用在 markSent() 前宕机，Outbox 仍是 PENDING，恢复后会再次发送。此处不能把它称为“恰好一次”；但 delete cache:shop:{id} 重复执行没有副作用，所以重复安全。

发送异常会按指数退避更新 next_retry_time，默认最多自动尝试 12 次；超过上限会标为 FAILED 停入人工处理区。因此准确说是“持久化重试并可观测地升级失败”，不是凭空保证永不失败。

8.4 消费者：每个应用实例都必须收到同一条失效事件

普通 Kafka 同一消费组会把一条消息分摊给组内某一个消费者，这不适合 L1 缓存失效：我们要让每一个 JVM都删除自己的 Caffeine。项目为每个 JVM 生成独立消费组：

# application.yaml
hmdp:
  kafka:
    shop-cache:
      consumer-group: ${spring.application.name}-shop-cache-${random.uuid}
      # 每个 JVM 的 groupId 不同，故每个 JVM 都会消费同一 Topic

# 关闭自动提交，手动即时确认
spring.kafka.consumer.enable-auto-commit: false
spring.kafka.listener.ack-mode: manual_immediate
// ShopCacheInvalidationKafkaConsumer：真实消费代码
@KafkaListener(topics = "${hmdp.kafka.shop-cache.topic}",
               groupId = "${hmdp.kafka.shop-cache.consumer-group}",
               containerFactory = "shopCacheKafkaListenerContainerFactory")
public void onMessage(ShopCacheInvalidationMessage message, Acknowledgment acknowledgment) {
    if (message == null || message.getShopId() == null || message.getEventId() == null) {
        throw new IllegalArgumentException("Invalid shop cache invalidation message");
    }
    consumerHandler.evict(message.getShopId()); // 成功清理后才 ACK
    acknowledgment.acknowledge();
}
// consumerHandler.evict()：清理时拿与更新/查询同一把 per-shop 写锁
@CacheConsistencyLock(name = "shop", key = "#p0", mode = CacheLockMode.WRITE)
public void evict(Long shopId) {
    invalidationHandler.evict(shopId); // Caffeine.invalidate + Redis.delete
}

如果清理成功：执行 ACK，Kafka 才提交当前 offset。如果 Redis 删除或加锁失败：方法抛异常，不 ACK，框架会按配置重试 3 次、每次间隔 1 秒；仍失败后同步投递 DLT，DLT 成功后才提交“已恢复”的 offset。删除是幂等的，因此重复投递、重复消费都安全。

这条链路的承诺：只要 Outbox 记录仍为 PENDING，Relay 就会持续尝试把事件送到 Kafka；每个 JVM 只在本机 L1/L2 清理完成后才 ACK。依托持久化 Outbox、Kafka 副本确认、重试/DLT，以及幂等删除，获得“最终每实例缓存失效”的至少一次语义。

9. 双重缓存最容易遗漏：更新后 L1 怎么失效？

如果只删本机 Caffeine，其他实例仍可能继续返回旧数据。因此项目更新店铺后发布失效事件；每个 JVM 使用独立 Kafka 消费组来消费同一条消息，并清掉自己的本地缓存。

// ShopServiceImpl.update()
if (!updateById(shop)) return Result.fail("店铺更新失败");
shopCacheInvalidationPublisher.publish(id);

// ShopCacheInvalidationKafkaConsumer.onMessage()
consumerHandler.evict(message.getShopId());
acknowledgment.acknowledge();

这是一种最终一致性设计：失效消息到达前，少量请求可能读到旧 L1；但 L1 自身 60 秒过期，并且 Kafka 失效通知会主动缩短陈旧窗口。对于商户详情这类读多写少、允许短暂陈旧的场景，这个取舍通常合理。

10. 最终复述：面试时如何讲这条链路

60 秒版本：商户详情是高频读接口，我使用 Caffeine 和 Redis 两级缓存。加 Caffeine 的原因是 Redis 对应用仍是远程调用，热点读每次都要经历网络和编解码；而 Caffeine 在 JVM 内直接命中，可以降低热点请求延迟和 Redis QPS。Redis 则负责跨实例共享。L1 未命中后，先用 Redis-backed Bloom Filter 拦截确定不存在的 ID，再查 Redis。Redis 中对不存在的商户保存短 TTL 的空字符串，避免同一个非法 ID 重复穿透。两层缓存都未命中时，用 Redisson 分布式锁保证多个实例里只有一个线程回源 MySQL 并重建缓存；没拿到锁的线程只会再次读缓存，不会一起打数据库。重建完成后同时回填 Redis 与本地缓存。店铺更新则通过失效事件通知各实例清理 L1，以最终一致性换取读性能。

高频追问自测

Q：为什么 Bloom 在 Redis 后面？

这里的 Bloom 在 Redis 前面。它对“确定不存在”的 ID 直接短路，减少 Redis/DB 无效访问；但它有误判，返回“可能存在”仍必须去 Redis/DB 验证。

Q：有 Bloom 了为什么还要空值缓存？

Bloom 会误判，且新增/初始化窗口中必须 fail-open；空值缓存能把实际回源后确认不存在的热点非法 ID 缓住，两者覆盖不同路径。

Q：为什么 Redisson 锁后还要二次查缓存？

等待锁的时间内，另一个实例可能已重建完成。二次检查能避免“拿到了锁就必查 DB”的无效回源，这就是双重检查。

Q：Redis 挂了怎么办？

这份查询实现的正常路径依赖 Redis 与 Redisson；Bloom 组件本身采用 fail-open，不会误拒绝真数据，但 Redis 读/锁不可用时会抛出异常。生产上应结合 Redis Sentinel、熔断降级或受控的 DB fallback，并评估 DB 承载能力；不能无条件放开所有请求回源。
